# BUG-CON-001 创建/更新产品版本接口返回 500（响应序列化触发懒加载 MissingGreenlet）



- **缺陷编号**：BUG-CON-001

- **发现日期**：2026-07-07

- **修复日期**：2026-07-07

- **所属端/模块**：运营后台端 / 产品版本管理

- **对应接口**：`POST /api/console/product-version`、`PUT /api/console/product-version/{id}`

- **对应需求**：`项目文档/02.需求文档/01.运营后台/**`（产品版本授权）

- **对应用例**：TC-CON-PRODUCT-002 / TC-CON-PRODUCT-003

- **严重级别**：S2 严重

- **状态**：已修复



## 复现步骤



1. 以管理员登录运营后台（`13800000000/admin123`）。

2. 调用 `POST /api/console/product-version`，body：`{"version_code":"test_ver_x","version_name":"测试版本"}`。

3. 观察响应。



## 期望结果



HTTP 200，`code=0`，返回新建版本对象（含 `id`、`versionCode`、`createdAt` 等）。



## 实际结果（修复前）



HTTP 500，`code=500`（生产环境经全局异常处理器返回；测试直连时抛 `pydantic_core.ValidationError`）。记录被 `flush` 但因响应序列化失败，请求最终回滚，**版本创建不成功**。



## 证据 / 报错



```

pydantic_core._pydantic_core.ValidationError: 2 validation errors for ProductVersionOut

created_at

  Error extracting attribute: StatementError: (sqlalchemy.exc.MissingGreenlet)

  greenlet_spawn has not been called; can't call await_only() here.

  Was IO attempted in an unexpected place?

[SQL: SELECT sys_product_version.created_at ... FROM sys_product_version WHERE id = %s]

updated_at

  Error extracting attribute: (同上)

app/modules/console/api/product/product_version.py:58: ValidationError

```



> 已在**真实提交路径**（不使用测试回滚 Session）复现，确认为生产缺陷，非测试基座造成。



## 根因分析（已定位）



- 涉及文件：

  - `backend/app/modules/console/api/product/product_version.py:57`（create）、`:72`（update）

  - `backend/app/modules/console/models/product/product_version.py`

  - `backend/app/modules/console/schemas/product/product_version.py`（`ProductVersionOut` 含 `created_at`/`updated_at`）

- 原因：`ProductVersionService.create_version` 仅 `db.add + db.flush` 后返回 ORM 对象；`created_at`/`updated_at` 为数据库 `server_default` 生成字段，`flush`（INSERT）后并未回填到实例。接口随即用 `ProductVersionOut.model_validate(version)` 序列化，pydantic 的 `from_attributes` 在 **Rust 侧同步** 访问这两个属性，触发 SQLAlchemy 异步懒加载 `await_only()`，但当前不在 greenlet 上下文中 → `MissingGreenlet`。

- 其他 CRUD（角色/字典/用户/AI 员工）之所以正常，是因为它们创建后只返回 `message` 或 `{"id": ...}`，未在同一请求内序列化含 `server_default` 时间戳的完整对象。



## 修复方案（已实施）



在 `ProductVersionService.create_version` / `update_version` 的 `await db.flush()` 之后增加 `await db.refresh(version)`，确保 `server_default`/`onupdate` 生成的时间戳已加载到 ORM 实例，再返回给 API 层序列化。



- 修改文件：`backend/app/modules/console/services/product/product_version_service.py`

- 回归：`TC-CON-PRODUCT-002`（创建+详情）、`TC-CON-PRODUCT-003`（更新）已通过自动化

# BUG-CON-002 参数校验失败误用 AuthException，返回 401 而非 400



- **缺陷编号**：BUG-CON-002

- **发现日期**：2026-07-07

- **修复日期**：2026-07-07

- **所属端/模块**：运营后台端 / 认证-个人配置

- **对应接口**：`PUT /api/console/auth/user-workplace-config`（`user-theme` 亦受影响）

- **对应需求**：`项目文档/02.需求文档/01.运营后台/**`（个人中心/工作台配置）

- **对应用例**：TC-CON-AUTH-016

- **严重级别**：S3 一般

- **状态**：已修复



## 复现步骤



1. 管理员登录后调用 `PUT /api/console/auth/user-workplace-config`。

2. body：`{"workplaceConfig": {"quickActions": ["1","2",...,"20"]}}`（超过 12 项上限）。



## 期望结果



HTTP 200 + `code=-1`（BizException 业务错误），提示「快捷操作最多 12 项」，属于**参数校验错误**，不应触发登录态失效语义。



## 实际结果（修复前）



HTTP 401，`code=401`。前端拿到 401 通常会触发「登录失效 → 跳转登录页 / 清 token」逻辑，误导用户，破坏体验。



## 证据 / 报错



```

AuthService._validate_workplace_config(...) raise AuthException("快捷操作最多 12 项")

→ 全局 auth_exception_handler 映射为 HTTP 401 / code=401

```



## 根因分析（已定位）



- 涉及文件：`backend/app/modules/console/services/auth/auth_service.py`

  - `_validate_workplace_config`（约 962~985 行）对 `quickActions` 类型/数量/元素的校验失败均 `raise AuthException(...)`。

- 原因：参数校验错误被当作认证异常抛出；`AuthException` 在 `app/common/exceptions.py` 中被映射为 HTTP 401，语义错误。



## 修复方案（已实施）



将 `_validate_workplace_config` 内的校验失败改为抛 `BizException`（HTTP 200 + `code=-1`），使「参数错误」与「未认证」语义分离。



- 修改文件：`backend/app/modules/console/services/auth/auth_service.py`

- 回归：`TC-CON-AUTH-005~006`（纯逻辑）、`TC-CON-AUTH-016`（HTTP 集成）已通过自动化
