# BUG-CLI-001 地名标准化：以「州」结尾的地级市省略「市」后缀时层级路径解析失败

- **缺陷编号**：BUG-CLI-001
- **发现日期**：2026-07-07
- **所属端/模块**：企业端 / 计费引擎 · 地名标准化
- **对应接口**：`POST /api/client/billing/calculate`（间接）、运单地名导入
- **对应需求**：`项目文档/02.需求文档/02.企业端/05.计费引擎模块/**`
- **对应用例**：TC-CLI-BILLING-101、TC-CLI-WAYBILL-050
- **严重级别**：S3 一般
- **状态**：待确认

## 复现步骤

1. 租户库中存在地级市，其标准名以「市」结尾但词干以「州」结尾（如 `沧州市`、`达州市`、`兰州市`）。
2. 以「省份/去掉后缀的城市名」形式调用地区标准化（等价于用户运单里只写「达州」而非「达州市」）：
   - `StandardizeService.resolve_region(db, raw_name="河北省/沧州")`
3. 与写全称对比：`resolve_region(db, raw_name="河北省/沧州市")`。

## 期望结果

两者都应解析到同一个地级市 `region_id`（层级路径匹配应能补全常见省略的「市」后缀）。

## 实际结果

- 写全称：命中，`matched_by=path`，`region_id=42`。
- 省略后缀：`region_id=None`，`matched_by=unresolved`（解析失败）。

## 证据 / 报错

本机租户库 `zt_biz_1001_ci` 实测（节选，已核对中文）：

```
expand('达州')  -> ['达州']          # 未生成 '达州市' 候选
expand('达州市') -> ['达州市']
full  '<省>/<城市市>' -> region_id=42, matched_by=path
omit  '<省>/<城市>'   -> region_id=None, matched_by=unresolved
```

## 根因分析

- 涉及文件：`backend/app/modules/client/services/billing/standardize_service.py:48`
  函数 `_expand_leaf_name_variants`：

```python
last_ch = s[-1]
if last_ch not in "省市县区盟州旗":
    for sfx in ("市", "地区", "盟", "州", "县", "区", "旗"):
        trials.append(s + sfx)
```

- 该判断把「州/盟/旗」等既可能是行政后缀、也可能是**地名词干末字**的字符，一律当成
  「已带后缀」而跳过候选补全。对于「达州/沧州/兰州/忻州/荆州/徐州」等以「州」结尾的
  **地级市**（库名实为「…州市」），省略「市」后无法生成 `…州市` 候选，层级路径匹配失败。

## 修复建议

- 后缀补全不应因末字属于「州/盟/旗」而整体跳过至少「市」候选。可改为：
  无论末字是否为 `州/盟/旗`，都追加 `市` 候选（并保留原值去重）；仅当末字确为 `市/省/县/区`
  时才认为已是完整行政后缀。
- 或维护一份「以州/盟/旗结尾的地级市」白名单参与后缀扩展。
- 补充回归用例覆盖 `达州/沧州/兰州` 等城市的省略后缀解析。

# BUG-CLI-002 AI 日志脱敏：身份证正则反向断言用 `\w`，与手机号/银行卡不一致

- **缺陷编号**：BUG-CLI-002
- **发现日期**：2026-07-07
- **所属端/模块**：企业端 / AI 数字人 · 日志脱敏
- **对应接口**：AI 工具调用日志落库（`ai/services` 内部）
- **对应需求**：`项目文档/02.需求文档/02.企业端/11.AI数字员工/**`
- **对应用例**：TC-CLI-AI-002
- **严重级别**：S4 轻微
- **状态**：待确认

## 复现步骤

1. 对紧邻中文（无空格分隔）的身份证号脱敏：
   - `desensitize_text("身份证110101199001011234")`

## 期望结果

按身份证规则脱敏为「前 6 位 + 8 位掩码 + 后 4 位」：`身份证110101********1234`。

## 实际结果

未走身份证规则，而是**回退到银行卡规则**被掩成 `身份证1101****1234`（前 4 + 掩码 + 后 4），
掩码位数与语义不符。更边界地，**15 位旧身份证号**紧邻中文时（不落入银行卡 16~20 位范围）
存在漏脱敏风险。

## 证据 / 报错

本机实测（已核对中文）：

```
desensitize_text('身份证110101199001011234') -> '身份证1101****1234'   # 期望 110101********1234
desensitize_text('电话13812345678')          -> '电话138****5678'      # 正常
desensitize_text('卡号6222021234567890123')  -> '卡号6222****0123'     # 正常
```

## 根因分析

- 涉及文件：`backend/app/modules/ai/security/desensitize.py:13-15`

```python
_PHONE   = re.compile(r"(?<!\d)(1\d{2})\d{4}(\d{4})(?!\d)")
_ID_CARD = re.compile(r"(?<!\w)(\d{6})\d{8}(\d{4})(?!\w)")   # ← 用 \w
_BANK_CARD = re.compile(r"(?<!\d)(\d{4})\d{8,12}(\d{4})(?!\d)")
```

- `_ID_CARD` 用 `(?<!\w)` / `(?!\w)`，而 Python 正则默认 Unicode 下**中文属于 `\w`**，
  故身份证号紧邻中文字符时反向断言失败，跳过身份证规则；随后落到 `_BANK_CARD`（`\d` 断言）
  被当作银行卡处理，掩码位数不符（前 4 后 4，而非身份证的前 6 后 4）。
- 手机号/银行卡都用 `\d` 断言，唯独身份证用 `\w`，规则不一致。

## 修复建议

- 将 `_ID_CARD` 的断言统一为数字边界：`(?<!\d)(\d{6})\d{8}(\d{4})(?!\d)`，与手机号/银行卡一致。
- 同时补充 15 位旧身份证兼容（可选：`(\d{6})\d{5}(\d{4})`），并保证脱敏顺序不会让身份证被银行卡规则抢先命中。
- 补充回归用例覆盖「中文紧邻身份证」「15 位旧身份证」两种边界。
