# BUG-DRV-001 我的任务列表接口在 MySQL 报 SQL 语法错误（1064）

- **缺陷编号**：BUG-DRV-001
- **发现日期**：2026-07-07
- **所属端/模块**：驾驶员 H5 端 / 任务流转
- **对应接口**：`GET /api/driver/task/my`
- **对应需求**：`项目文档/02.需求文档/03.移动端/02.驾驶员H5端/02.任务流转与司机动作.md`
- **对应用例**：TC-DRV-TASK-001
- **严重级别**：S1 致命（司机端首页"我的任务"列表完全不可用）
- **状态**：已修复

## 修复说明

- `driver_task_service.py` 排序改为 `Task.planned_load_time.is_(None).asc()` + `desc()`，MySQL 兼容。
- `test_list_my_tasks_empty` 已改为正常断言并通过。

## 复现步骤（修复前）

1. 以任意在职司机登录 H5，进入"我的任务"页（或直接调 `GET /api/driver/task/my`）。
2. 后端执行 `DriverTaskService.list_my_tasks` 的排序查询。
3. 观察 MySQL 返回错误。

自动化复现：`cd backend && python -m pytest tests/driver/test_driver_task_service.py::TestTaskIntegration::test_list_my_tasks_empty -v`
（当前标记 `xfail`，DB 可连接时稳定命中该错误）。

## 期望结果

返回 `{ code: 0, data: { list: [], total: 0 } }`，按计划装车时间倒序、NULL 排末尾。

## 实际结果

MySQL 抛 1064 语法错误，接口 500：

```
sqlalchemy.exc.ProgrammingError: (pymysql.err.ProgrammingError) (1064,
"You have an error in your SQL syntax; ... near 'NULLS LAST, biz_task.id DESC
 LIMIT 0, 15' at line 3")
[SQL: ... ORDER BY biz_task.planned_load_time DESC NULLS LAST, biz_task.id DESC LIMIT %s, %s]
```

`total`（count 查询）能返回，但列表查询因 `ORDER BY ... NULLS LAST` 崩溃——
**MySQL 不支持 `NULLS LAST` 语法**（仅 PostgreSQL/Oracle 支持）。

## 根因分析

- 涉及文件：`backend/app/modules/driver/services/driver_task_service.py:167`
- 代码：
  ```python
  .order_by(Task.planned_load_time.desc().nullslast(), Task.id.desc())
  ```
- SQLAlchemy 的 `.nullslast()` 在 MySQL 方言下直接输出字面量 `NULLS LAST`，而 MySQL 无该语法，导致 SQL 解析失败。

## 修复建议

MySQL 需用 `ISNULL()` 或列的 `IS NULL` 表达式模拟：

```python
from sqlalchemy import case
# 方案 A：NULL 排末尾（等价 nullslast）
.order_by(
    (Task.planned_load_time.is_(None)).asc(),   # False(0) 在前，True(1) 在后
    Task.planned_load_time.desc(),
    Task.id.desc(),
)
```

或移除 `.nullslast()`（MySQL 默认 NULL 在 `DESC` 时排最后，`ASC` 时排最前，可满足多数场景）。
建议同时排查企业端 `client/services/task/*` 是否有同类 `nullslast()/nullsfirst()` 用法。

# BUG-DRV-002 回单表在租户库缺失，且需求"占位不落表"口径与落表实现不一致

- **缺陷编号**：BUG-DRV-002
- **发现日期**：2026-07-07
- **所属端/模块**：驾驶员 H5 端 / 回单签收与凭证上传
- **对应接口**：`POST /api/driver/task-receipt/upload`、`GET /my`、`DELETE /{id}`
- **对应需求**：`项目文档/02.需求文档/03.移动端/02.驾驶员H5端/04.回单签收与凭证上传.md`
- **对应用例**：TC-DRV-RECEIPT-001/002/003/006
- **严重级别**：S2 严重（回单上传/查询/删除全链路在测试库不可用）
- **状态**：已修复

## 修复说明

- 迁移 `20260707_003_add_biz_task_receipt.py` 补充 `CREATE TABLE IF NOT EXISTS biz_task_receipt`。
- 采纳落表版实现；`biz_task_receipt` 已在 `sys_product_feature.required_tables` 中登记。

## 复现步骤（修复前）

1. 以在职司机对某任务上传回单：`POST /api/driver/task-receipt/upload`。
2. `DriverReceiptService.create_receipt` 向 `biz_task_receipt` 插入。
3. 观察数据库错误。

自动化复现：`cd backend && python -m pytest tests/driver/test_driver_receipt_service.py -v`
（3 个集成用例因表缺失被 `skip`）。

## 期望结果

回单成功落表并可查询/删除；或若坚持一期"占位不落表"，接口应返回 `stored:false` 且不触表。

## 实际结果

```
pymysql.err.ProgrammingError: (1146, "Table 'zt_biz_1001_ci.biz_task_receipt' doesn't exist")
[SQL: INSERT INTO biz_task_receipt (...) VALUES (...)]
```

## 根因分析

存在两处口径冲突：

1. **代码 vs 数据库**：`backend/app/modules/client/models/task/task_receipt.py` 已定义 `TaskReceipt` 模型且 service 走真实 `INSERT`，但测试租户库 `zt_biz_1001_ci` 未建 `biz_task_receipt` 表（迁移/`required_tables` 未在该库落地）。
2. **代码 vs 需求**：需求文档 `04 §四` 明确写"回单接口一期为**占位实现**……**不落表**（response 携带 `stored: false`）……`biz_task_receipt` 待 v0.2 引入"，但当前实现已是**落表版**（含 `DELETE`、`item_id`/`dispatch_order_id`/`receipt_type` 字段）。

- 涉及文件：
  - `backend/app/modules/driver/services/driver_receipt_service.py:66-79`（INSERT）
  - `backend/app/modules/client/models/task/task_receipt.py`（模型）
  - `项目文档/02.需求文档/03.移动端/02.驾驶员H5端/04.回单签收与凭证上传.md:66-88`（占位口径）

## 修复建议

- 若采纳落表版（推荐，功能更完整）：在租户库建表并纳入迁移/`sys_product_feature.required_tables`，**同步更新需求文档 04**，删除"占位/不落表/v0.2"表述。
- 若坚持一期占位：回退 service 为不落表实现，返回 `stored:false`。
- 二者择一，消除文档与代码分歧。

# BUG-DRV-003 撤销签收接口未强制 `operation:task:revert-sign` 权限

- **缺陷编号**：BUG-DRV-003
- **发现日期**：2026-07-07
- **所属端/模块**：驾驶员 H5 端 / 任务流转（撤销签收）
- **对应接口**：`POST /api/driver/task/items/{itemId}/revert-sign`
- **对应需求**：`项目文档/02.需求文档/03.移动端/02.驾驶员H5端/00.模块总览.md §六`、`02.任务流转与司机动作.md §三.3.5`
- **对应用例**：TC-DRV-TASK-012
- **严重级别**：S3 一般（受限动作被放开，越权风险）
- **状态**：已修复

## 修复说明

- `DriverTaskService.revert_sign_item` 增加 `operation:task:revert-sign` 菜单权限校验（复用 `PermissionGuard.user_has_menu_permission`）。
- 集成用例 `test_revert_sign_without_permission_rejected` 已覆盖。

## 复现步骤（修复前）

1. 以普通在职司机（未授予 `operation:task:revert-sign`）登录。
2. 对 `item.status=3` 的挂接行调 `POST /api/driver/task/items/{itemId}/revert-sign`，`reason` 合法。
3. 观察是否被权限拦截。

## 期望结果

需求 `00 §六` 与 `02 §三.3.5` 要求撤销签收"受限（需 `operation:task:revert-sign`）"，
无权限的司机应被拒（403 / PermissionException）。

## 实际结果

接口仅依赖 `get_current_user` + `get_tenant_db`，无任何权限校验；
`DriverTaskService.revert_sign_item` 仅校验 `item.status==3`，任何在职司机均可撤销签收。

## 根因分析

- 涉及文件：`backend/app/modules/driver/api/task.py:138-147`（`revert_sign_item` 路由缺少权限依赖）
- `services/driver_task_service.py:397-413`（`revert_sign_item` 无权限判定）
- 需求声明的 `operation:task:revert-sign` 权限点未在代码中落地校验。

## 修复建议

在 `revert_sign_item` 路由增加权限依赖（参考 client 端 `require_permission("operation:task:revert-sign")` 的实现方式），
或在 service 内基于 `DriverContext` 的角色/权限做校验；并为该权限点补充签发与运营侧配置。
