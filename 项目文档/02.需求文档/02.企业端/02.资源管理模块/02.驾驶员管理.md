# 企业端资源模块 - 驾驶员管理

> **所属阶段**：阶段四 - 企业端资源模块
>
> **文档状态**：已完成
>
> **优先级**：高（资源模块核心基础）

## 一、功能概述

驾驶员管理是物流运力体系的核心基础模块。在物流运输系统中，一个可用的运力由**司机 + 车辆（+ 挂车）**构成，驾驶员数据是开展后续业务的前置条件。本模块聚焦驾驶员全生命周期信息管理，为后续运力组合、运单派车、调度排班提供人员数据支撑。

核心设计原则：

- **多表解耦**：驾驶员信息按职责域拆分为「核心身份」「资质信息」「运营属性」「账户结算」四张表，各表独立演进、互不干扰
- **双状态体系**：人事状态（在职/离职/冻结）与运营状态（可接单/忙碌/休假/停运）分离，人事状态由 HR 管理，运营状态由调度/业务驱动
- **账户多开**：一个驾驶员可拥有多个结算账户（银行卡、油气款、积分等），适配物流行业多经营主体的结算场景

## 二、业务背景

### 核心业务诉求

1. **运力基础数据**：驾驶员是物流运力的核心要素，所有业务模块（运单、调度、结算）都需要引用驾驶员信息，因此驾驶员管理是业务开展的前置条件
2. **资质合规管理**：驾驶证、从业资格证的有效期管理是合规运营的基本要求，需要集中管理并支持到期预警
3. **灵活的运营管理**：不同类型的司机（自有/外协/临时）管理策略不同，需要按车队（部门）组织并支持运营状态流转
4. **多主体结算**：物流公司通常有多个经营主体，同一司机在不同主体下可能有不同的结算账户

### 3.3 删除驾驶员

- 软删除（`is_deleted = 1`），驾驶员数据不物理删除
- 删除前校验：如驾驶员已关联正在进行中的运单，则禁止删除并提示
- 删除时自动将关联的资质、运营属性、账户记录同步标记删除

### 3.4 状态定义

**人事状态（`biz_driver.status`）**：

| 状态值 | 状态名称 | 说明 |
|--------|---------|------|
| 1 | 在职 | 正常在岗，可被分配运营任务 |
| 0 | 冻结 | 暂时冻结，不可接单但保留信息 |
| 2 | 离职 | 已离职，终态 |

**运营状态（`biz_driver_operation.operation_status`）**：

| 状态值 | 状态名称 | 说明 |
|--------|---------|------|
| 1 | 可接单 | 空闲状态，可派单 |
| 2 | 忙碌 | 正在执行运输任务（后期由运单模块驱动） |
| 3 | 休假 | 休假中，不可派单 |
| 4 | 停运 | 因故停运（如证件过期） |

> **说明**：人事状态与运营状态分离。人事状态为「在职」的司机才参与运营状态流转；「冻结」或「离职」的司机不出现在可派单列表中。

### 3.5 司机编号生成规则

格式：`D` + 年份(4位) + 序号(4位)，如 `D20260001`。

- 新增驾驶员时由后端自动生成，前端不可编辑
- 序号在同一租户内自增，支持每年最多 9999 个新增驾驶员
- 如超出 4 位则自动扩展位数

### 6.3 前后端字段适配方案

前端 TypeScript 模型使用小驼峰命名（`driverCode`、`licenseType`），后端 ORM 使用下划线命名（`driver_code`、`license_type`）。在**后端 Schema 层的 `from_model()` 方法中做映射转换**，与项目现有模式一致。

创建/更新请求中核心字段、资质字段和运营字段合并提交，后端 Service 层负责拆分：
1. 从请求体中提取核心字段，写入 `biz_driver`
2. 从请求体中提取资质字段，写入 `biz_driver_license`
3. 从请求体中提取运营字段，写入 `biz_driver_operation`
4. 账户信息通过独立接口管理（1:N 关系）
5. 查询响应时 LEFT JOIN 关联表，合并输出
