# 计费引擎部署与运维手册

> 适用版本：运费匹配引擎升级（Phase 1~8）后的所有版本
> 最近更新：2026-05-13

本手册记录运费匹配引擎升级后新增的运行时组件、首次/日常发版的注意事项，以及常用运维手动命令。**`bash deploy/deploy.sh update` 已经覆盖日常更新流程**，本手册只补充该流程之外需要人工关注的事项。

---

## 1. 运行时组件总览

升级后线上一共 4 个 docker 容器：

| 容器名 | 镜像 | 角色 | 是否新增 |
|---|---|---|---|
| `zhitu-redis` | redis:7-alpine | 缓存 | 否 |
| `zhitu-backend` | Dockerfile.backend | FastAPI HTTP 服务（4 个 uvicorn worker） | 否 |
| **`zhitu-backend-worker`** | Dockerfile.backend（同上） | **计费引擎专用 worker（单实例）** | **是** |
| `zhitu-nginx` | Dockerfile.nginx | 反向代理 + 前端静态资源 | 否 |

### 1.1 为什么 worker 要独立成容器

- **资源隔离**：合同变更触发上千运单批量重算时，不会拖慢 API 响应。
- **避免重复扫表**：`zhitu-backend` 启动了 4 个 uvicorn 进程；如果在每个进程内都嵌入 scheduler，等于 4 个 worker 同时抢任务，存在重复执行的极小概率。
- **独立扩缩容**：未来运单量翻 10 倍以上可直接 `docker compose up -d --scale backend-worker=N`，worker 内部已具备行级抢占语义。

### 1.2 关键环境变量

由 `deploy/docker/docker-compose.yml` 定义，按需在宿主机 `.env` 覆盖：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `FREIGHT_CALC_WORKER_ENABLED` | backend = `0`，backend-worker = `1` | API 进程是否内嵌 scheduler；生产**必须保持 backend = 0** |
| `FREIGHT_CALC_WORKER_INTERVAL` | `5`（秒） | 扫表轮询间隔 |
| `FREIGHT_CALC_WORKER_BATCH` | `20` | 单租户单轮处理任务上限 |

## 2. 首次升级到本版本的执行顺序（**重要**）

老库升级到本版本必须按以下顺序操作；之后的常规发版直接 `bash deploy/deploy.sh update --auto` 即可。

### 2.1 拉新代码 + 重建镜像 + 启动新容器

```bash
cd /opt/zhitu
sudo bash deploy/deploy.sh update --auto
```

> `docker compose up -d --build` 会自动 build 并起新增的 `zhitu-backend-worker` 容器。

### 2.2 验证 worker 容器健康

```bash
sudo docker ps | grep zhitu
# 应看到 4 个容器：zhitu-redis / zhitu-backend / zhitu-backend-worker / zhitu-nginx

sudo docker logs zhitu-backend-worker --tail 30
# 期望日志：
#   [freight-worker] 启动 env=production platform_db=zt_platform
#   [FreightCalcWorker] 已启动，间隔 5s，每租户每轮 20 条
```

### 2.3 数据库迁移（**首次升级必须做一次**）

> ⚠️ 此时 worker 容器已经在轮询，但**老租户库还没有计费引擎的新表**，worker 会瞬时报 `Table 'xxx.biz_freight_calc_task' doesn't exist`，这是预期的。worker 已经具备「同租户表缺失只警告一次后跳过」的容错，**不会刷屏**。

执行迁移（DDL + 历史数据回填，幂等可重复执行）：

```bash
# 全租户
sudo docker exec -it zhitu-backend python scripts/fix/migrate_freight_engine.py --all

# 或：单租户试点
sudo docker exec -it zhitu-backend python scripts/fix/migrate_freight_engine.py 1001
```

迁移完成后需要让 worker 重新检测租户表：

```bash
sudo docker restart zhitu-backend-worker
sudo docker logs zhitu-backend-worker --tail 30   # 不应再有 1146 报错
```

### 2.4 双引擎对比回归（建议做）

`dual_engine_regression.py` 用历史 `biz_waybill.freight_amount` 与新引擎 dry_run 结果做差异对比，输出报表给运营核对：

```bash
# 全租户每库取最新 200 单
sudo docker exec -it zhitu-backend python scripts/fix/dual_engine_regression.py --all --limit 200
```

### 2.5 拷出报表

```bash
sudo mkdir -p /opt/zhitu/data/freight_reports
sudo docker cp zhitu-backend:/app/reports/. /opt/zhitu/data/freight_reports/
ls -lt /opt/zhitu/data/freight_reports | head
```

报表两份：
- `freight_regression_<tenant>_<时间戳>.json`：完整字段（编程友好）
- `freight_regression_<tenant>_<时间戳>.csv`：UTF-8 BOM，Excel 直接打开

CSV 的 `状态 / 错误类型 / 错误信息` 列用于人工核对：

| 状态 | 含义 |
|---|---|
| `identical` | 新旧引擎金额一致（差 ≤ 0.01） |
| `minor_diff` | 差异 ≤ 1 元 |
| `major_diff` | 差异 > 1 元，**重点核对** |
| `new_unmatched` | 新引擎匹配不到，看 `错误类型`：<br/>`CONTRACT_NOT_FOUND`：客户在该日期无生效合同<br/>`RULE_NOT_FOUND`：合同下没匹配运价<br/>`AREA_NOT_RECOGNIZED`：地名标准化失败（缺别名）<br/>`SERIES_NOT_RECOGNIZED`：车型标准化失败（缺别名） |
| `old_missing` | 历史就没填 freight_amount |

通过率 = `(identical + minor_diff) / total`，达到 95%+ 即可放心切流。

## 3. 日常运维命令

### 3.1 容器与日志

```bash
# 看所有容器
sudo docker ps | grep zhitu

# 看 worker 实时日志
sudo docker logs -f zhitu-backend-worker --tail 100

# 看 backend 实时日志
sudo docker logs -f zhitu-backend --tail 100

# 重启 worker（修改 .env 后必须重启）
sudo docker restart zhitu-backend-worker

# 单独拉起 worker
cd /opt/zhitu/deploy/docker
sudo docker compose up -d backend-worker

# 临时停 worker（计算会全部 pending，旧 freight_amount 仍可用）
sudo docker stop zhitu-backend-worker
```

### 3.2 调度参数调优

```bash
# /opt/zhitu/.env
FREIGHT_CALC_WORKER_INTERVAL=5      # 扫表间隔（秒）
FREIGHT_CALC_WORKER_BATCH=20        # 每租户每轮处理上限
```

改完后：
```bash
sudo docker compose -f /opt/zhitu/deploy/docker/docker-compose.yml restart backend-worker
```

### 3.3 手动触发某条运单重算

```bash
# 进 backend 容器交互式 python
sudo docker exec -it zhitu-backend python -c "
import asyncio
from app.core.database import db_manager
from app.modules.client.services.billing.freight_calc_task_service import (
    FreightCalcTaskService, TASK_MANUAL_RECALC,
)

async def main():
    await db_manager.init_platform_db()
    db_manager._get_or_create_tenant_engine('1001')
    factory = db_manager._tenant_session_factories['1001']
    async with factory() as s:
        task = await FreightCalcTaskService.enqueue_waybill_recalc(
            s, waybill_id=123, task_type=TASK_MANUAL_RECALC, priority=20,
        )
        await s.commit()
        print(f'enqueued task#{task.id}')

asyncio.run(main())
"
# 几秒后 worker 日志能看到执行
```

### 3.4 直接 SQL 看任务/异常

```sql
-- 待处理任务
SELECT * FROM zt_biz_1001.biz_freight_calc_task
WHERE status='pending' ORDER BY priority DESC, created_at DESC LIMIT 20;

-- 失败任务（含重试）
SELECT * FROM zt_biz_1001.biz_freight_calc_task
WHERE status='failed' ORDER BY id DESC LIMIT 50;

-- 待处理异常（业务异常，需要运营介入）
SELECT * FROM zt_biz_1001.biz_freight_calc_exception
WHERE process_status='pending' ORDER BY id DESC LIMIT 50;
```

## 4. 故障排查

### 4.1 worker 启动报 1146 / `Table doesn't exist`

- **原因**：该租户库还没跑过 `migrate_freight_engine.py`
- **现象**：worker 会针对每个有问题的租户**只警告一次**，然后静默跳过该租户
- **修复**：
  ```bash
  sudo docker exec -it zhitu-backend python scripts/fix/migrate_freight_engine.py <tenant_code>
  sudo docker restart zhitu-backend-worker   # 让 worker 重新检测
  ```

### 4.2 任务一直 pending 不被处理

排查清单：
1. `sudo docker ps | grep zhitu-backend-worker` —— worker 容器是否在运行
2. `sudo docker logs zhitu-backend-worker --tail 50` —— scheduler 是否启动 + 有没有报错
3. `sudo docker exec zhitu-backend-worker env | grep FREIGHT_CALC_WORKER_ENABLED` —— 是否为 `1`
4. SQL 查 `biz_freight_calc_task` 表 `status` 字段；如果都是 `running` 但没 `started_at` → worker 死锁，重启 worker

### 4.3 worker 与 backend 重复扫表

如果发现 task 偶发重复执行：
1. 检查 backend 的 `FREIGHT_CALC_WORKER_ENABLED` 必须为 `0`
   ```bash
   sudo docker exec zhitu-backend env | grep FREIGHT_CALC_WORKER_ENABLED
   ```
2. 检查是否手动跑了多个 `backend-worker` 实例
   ```bash
   sudo docker ps --filter name=zhitu-backend-worker
   ```

### 4.4 临时回滚到 backend 内嵌 worker

如果独立 worker 容器异常但又不想阻塞业务，可临时让 backend 内嵌 worker 兜底：

```bash
# 1) 停掉独立 worker
sudo docker stop zhitu-backend-worker

# 2) 临时让 backend 内嵌 worker
echo 'FREIGHT_CALC_WORKER_ENABLED=1' | sudo tee -a /opt/zhitu/.env
sudo docker compose -f /opt/zhitu/deploy/docker/docker-compose.yml up -d backend
```

> 此模式下 4 个 uvicorn 进程都会跑 worker，存在并发抢任务的极小概率重复执行（业务上仍然正确，只是会浪费一次计算）。问题修复后务必切回独立 worker 模式：
> ```bash
> sudo sed -i '/^FREIGHT_CALC_WORKER_ENABLED=1$/d' /opt/zhitu/.env
> sudo docker compose -f /opt/zhitu/deploy/docker/docker-compose.yml up -d backend backend-worker
> ```
