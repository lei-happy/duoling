## 二、判定标准

1. **写链路**：用真实 Service 串起单据全生命周期，逐步断言状态、金额、锁定标记与审计事件；所有写操作在单个事务内完成，结束 `rollback`，不污染租户库。
2. **反向闸口**：越权、越额、越级、重复等动作必须被 `BizException` 拦住，且拦截文案是业务口吻（不含字段名 / 状态码）。
3. **金额口径**：净额、税额、分摊必须逐笔对账到分，不接受「大致相等」。
4. **只读接口**：返回业务成功即算通过；本地库数据稀薄（见 §六.4），只读用例只能证明「查得动、不炸」。

## 六、本轮发现并修复的缺陷

### 1. 销项发票与打款批次建单必失败（阻断级，2 处）

`biz_customer_invoice` / `biz_payment_batch` 的 `planned_amount` 是 NOT NULL 且无默认值，但两个 Service 的建单构造器都没赋值——金额是建完关联明细后才由 `_refresh_amounts` / `refresh_totals` 汇总回填的，于是第一次 `flush()` 就撞 `Column 'planned_amount' cannot be null`。这意味着**开票申请与打款批次这两个功能完全不可用**，任何用户点击「新建」都会 500。

修复：建单时占位 `planned_amount=Decimal("0")`，由后续汇总回填。已顺带核对全部 10 个财务单据的建单构造器，现已全部赋值。

- `app/modules/client/services/finance/customer/customer_invoice_service.py`
- `app/modules/client/services/finance/cashier/payment_batch_service.py`

### 2. 销项票状态机缺「申请中 → 已开票」（阻断级）

`customer_invoice` 的可用状态集是 `{0,1,3,4,9}`（没有「已审批」这一环），但通用跳转表里 `1 → {0,2,4}`，特有跳转只补了 `3 → 9`。结果财务在开票系统开完票回来登记结果时，必然被状态机拦成「不能直接跳转到已开票」——**发票开出去了，系统里永远登记不进去**。

修复：`DOC_KIND_TRANS_EXTRA["customer_invoice"]` 补 `1: {3}`，并把这条设计意图写进注释。

- `app/modules/client/services/finance/base/finance_state_machine.py`

### 3. 对账行调整会吃掉分位残差（金额级，2 处）

建行时行金额以**运单运费 / 任务成本**为准，单价是 `金额 ÷ 台数` 取两位小数的派生值——按台常除不尽（1000 元 3 台 → 333.33）。这本是文档 02/03 §3.5 明确的口径（「以运费为准，不按乘积」，就是为了不因取整少收几分钱）。但 `adjust_line` 无条件按 `数量 × 单价 + 调整额` 重算，于是**只要有人碰一次调整额，账面就凭空少掉一分**，且每加一行就多丢一分，对账单越大越难解释。

修复：只有显式传了 `quantity` 或 `unit_price` 时才按乘积重算基数；只改调整额时沿用建行基数（`当前金额 - 原调整额`）。客户侧与承运商侧同步修复；司机工资单的提成本身就是「数量 × 单价」，不存在该问题，未改。

- `app/modules/client/services/finance/customer/customer_recon_service.py`
- `app/modules/client/services/finance/carrier/carrier_recon_service.py`

### 4. 新增前端文件行尾与格式不合仓库规范（工程规范）

本次新增的 35 个财务前端文件是 CRLF 行尾，而仓库既有文件在工作区均为 LF，`eslint` 报出 1.5 万条 `Delete ␍`，另有 73 处 prettier 换行不合规。已用 `eslint --fix` 全部归正（这些文件尚未纳入版本控制，转换不产生 diff 噪音），并重跑构建确认无副作用。

## 七、未覆盖范围与已知风险

1. **无 UI 端到端**：本轮只跑了构建与 lint，没有跑 Playwright 菜单冒烟。14 个页面的交互（弹窗校验、按钮权限位、导出下载）尚未自动化验证，建议补一轮 `client_menu_smoke` 级别的进入性冒烟。
2. **无 pytest 用例**：财务模块 24 张表、194 条路由目前没有一条 `tests/client` 用例，回归完全依赖本轮新增的 3 个 verify 脚本。这三个脚本已按仓库既有约定落到 `backend/scripts/verify/`，可重复执行、默认回滚；但它们依赖本地库有业务数据（任务 / 运单 / 客户 / 承运商），不能进 CI。若要进 CI，需要把候选池改成完全自建 fixture。
3. **pytest 4 项失败与财务无关**：`tests/client/test_task_alert_integration.py` 的 4 个用例失败，原因是本地租户库里 `biz_task_alert_rule` 的 `DISPATCH_TIMEOUT` 规则被人工配过（`rule_version=4`，`plan_enabled=0`），而用例只给了计划装车时间、没给要求时间，规则按计划时间那一路被关掉了，自然不产生预警。属本地规则配置导致的用例环境依赖，非代码回归——但也说明这几个用例对 DB 配置过敏，建议改为在用例内自建规则行。
4. **只读接口是在近乎空表上通过的**：本地库财务表几乎没有存量数据（客户对账单 1 条、客户结算单 1 条，第 3、4 期表全为 0 行），所以只读用例证明的是「SQL 与序列化不炸」，**没有验证多数据量下的口径正确性与性能**。经营核算六个维度全部返回 0 行，其口径正确性只在 §三 的分摊纯函数层面得到验证。
5. **写操作幂等键仍未落地**：`idempotency_key` 列已建但无人写入，网络重试可能产生重复单据。这一点已记在差距清单，本轮未处理。
6. **分配类接口入参键名不统一**：核销 / 关联类方法的金额键只有收款单认领（`receipt_voucher_service.claim`）用 `amount`，客户 / 承运商结算单关联对账、进项票核销、销项票关联结算四处都用 `appliedAmount`。API 层各自映射，对外无感，但写脚本或加新单据时极易传错键（本轮就在这上面踩过一次），建议统一到 `appliedAmount`。

## 九、结论

财务结算模块第 0~4 期的**后端业务链路可以交付**：对账 → 结算 → 收付 → 发票 → 核算的正向流程、逆向撤销、跨单据锁定与审计留痕均已逐笔验证到分。

但必须记下一点：本轮在写链路测试中才发现「销项票建单」「打款批次建单」「开票登记」三处**一点就报错的阻断级缺陷**——它们能一路通过静态检查、drift 检查、菜单核对与前端构建而不被发现，说明此前的验证手段（只读冒烟 + 页面打得开）不足以为财务这类写重模块背书。后续新增财务功能，写链路脚本应与代码同轮提交。

前端仅完成构建与 lint 级验证，页面交互仍需一轮人工或 Playwright 冒烟才能给出交付结论。
