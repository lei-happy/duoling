# BUG-OPN-001 LITE 运力上报占位接口因开放路径无租户上下文永远不可用



- **缺陷编号**：BUG-OPN-001

- **发现日期**：2026-07-07

- **修复日期**：2026-07-07

- **所属端/模块**：开放接口 / LITE 承运商运力上报

- **对应接口**：`POST /api/open/lite/carrier/task/{task_id}/dispatch`

- **对应需求**：`doc/02.需求文档/03.LITE端/承运商运力上报.md`

- **对应用例**：TC-OPN-LITE-004 / TC-OPN-LITE-005 / TC-OPN-LITE-007

- **严重级别**：S2 严重

- **状态**：已修复



## 复现步骤



1. 携带 `X-Lite-Token: dummy-token` 与合法请求体（mainDriverName / mainDriverPhone / plateNumber）POST 该接口。

2. 观察响应。



## 期望结果



按需求 3.2：先校验 token 非空 → 校验任务 `carrier_type=2` 且 `status=0` → 调用 `assign_carrier` 推进 `0→1`。



## 实际结果（修复前）



HTTP 400，`{"code":400,"message":"缺少租户信息，请确认登录状态"}`。请求根本无法进入 handler 主体，token 与任务状态校验形同虚设，接口在任何入参下都不可用。



## 证据 / 报错



```

POST /api/open/lite/carrier/task/1/dispatch  →  400

{"code": 400, "message": "缺少租户信息，请确认登录状态", "data": null}

```



## 根因分析



- 涉及文件：

  - `backend/app/core/middleware.py:58-71`（`TenantMiddleware.SKIP_PATHS` 含 `/api/open/`，对开放路径**跳过** token 解析，`request.state.tenant_code` 恒为 None）

  - `backend/app/modules/open/api/lite_carrier_dispatch.py:50`（handler 依赖 `db: AsyncSession = Depends(get_tenant_db)`）

  - `backend/app/core/dependencies.py:51-56,100-105`（`get_tenant_db → get_tenant_code`，缺租户即抛 `TenantException` → 400）

- 原因：接口位于 `/api/open/*`（被中间件视为无认证放行路径），却依赖需要租户上下文的 `get_tenant_db`；而开放路径不会解析任何能提供 `tenant_code` 的 token，导致依赖注入阶段必然失败，早于 handler 内的 token / 任务状态校验。此外 token 校验顺序也无法生效（校验逻辑写在 handler 内，永远执行不到）。



## 修复说明



- **改动文件**：`backend/app/modules/open/api/lite_carrier_dispatch.py`

- **方案**：移除 `get_tenant_db` 依赖；新增 `_parse_lite_tenant_code`，从 `X-Lite-Token` JWT 载荷（`tenant_code` / `tenant`）或查询参数 `tenant_code` 解析租户；通过 `db_manager.get_tenant_session(tenant_code)` 显式获取租户库 session；token 非空校验先于切库执行。

- **验证**：`backend/tests/open/test_lite_carrier_dispatch.py` — TC-OPN-LITE-004/005/007 通过。

# BUG-OPN-002 短信发送接口未校验手机号格式，任意字符串可落表生成验证码



- **缺陷编号**：BUG-OPN-002

- **发现日期**：2026-07-07

- **修复日期**：2026-07-07

- **所属端/模块**：开放接口 / 短信验证码

- **对应接口**：`POST /api/open/sms/send`

- **对应需求**：官网企业注册 / 登录 / 重置密码短信通道

- **对应用例**：TC-OPN-SMS-009

- **严重级别**：S3 一般

- **状态**：已修复



## 复现步骤



1. POST `/api/open/sms/send`，body `{"phone":"abc","purpose":4,"app_type":"website"}`。



## 期望结果



对非法手机号（不匹配 `^1[3-9]\d{9}$`）直接拒绝，返回参数校验错误，不落库、不生成验证码。



## 实际结果（修复前）



`SmsSendRequest.phone` 仅声明为 `str`，无格式/长度校验；用途 4（企业注册）时 `_check_phone_exists` 查不到用户即 `return`，随后生成 6 位验证码并以 `phone="abc"` 落 `sms_code` 表。可被用于制造垃圾记录 / 刷验证码。



## 证据 / 报错



```python

# backend/app/modules/open/api/sms.py:17-25

class SmsSendRequest(BaseModel):

    phone: str = Field(description="手机号")   # ← 无 pattern / min_length

    purpose: int = ...

    app_type: str = ...

```



## 根因分析



- 涉及文件：`backend/app/modules/open/api/sms.py:17-25`、`backend/app/modules/open/services/sms_service.py:113-160`

- 原因：入口 schema 与 service 均未做手机号格式校验（对比 `register` 侧 `RegisterPayload.validate_mobile` 有校验）。



## 修复说明



- **改动文件**：`backend/app/modules/open/api/sms.py`

- **方案**：在 `SmsSendRequest` 与 `SmsResetPasswordRequest` 增加 `@field_validator("phone")`，正则 `^1[3-9]\d{9}$`，与注册侧一致。

- **验证**：`backend/tests/open/test_sms.py` — TC-OPN-SMS-009 通过（非法手机号 HTTP 422）。

# BUG-OPN-003 验证码重发频率限制可被"已消费"记录绕过



- **缺陷编号**：BUG-OPN-003

- **发现日期**：2026-07-07

- **修复日期**：2026-07-07

- **所属端/模块**：开放接口 / 短信验证码

- **对应接口**：`POST /api/open/sms/send`

- **对应需求**：验证码重发间隔 60 秒

- **对应用例**：TC-OPN-SMS-010

- **严重级别**：S3 一般

- **状态**：已修复



## 复现步骤



1. 对某手机号发送验证码（生成 status=0 记录）。

2. 完成一次验证使该验证码被消费（`status` 置 1）。

3. 60 秒内再次请求发送验证码。



## 期望结果



无论上一条验证码是否已被使用，60 秒内的重复发送都应被"发送过于频繁"拦截。



## 实际结果（修复前）



重发检测查询条件含 `SmsCode.status == 0`，仅统计"未使用"记录。上一条被消费后（`status=1`）不再命中，60 秒内可立即再次发送，突破重发节流。



## 证据 / 报错



```python

# backend/app/modules/open/services/sms_service.py:134-146

last = await db.execute(

    select(SmsCode).where(

        SmsCode.phone == phone,

        SmsCode.purpose == purpose,

        SmsCode.status == 0,          # ← 仅未使用记录参与节流

    ).order_by(SmsCode.created_at.desc()).limit(1)

)

```



## 根因分析



- 涉及文件：`backend/app/modules/open/services/sms_service.py:134-146`

- 原因：节流查询把 `status==0` 作为条件，使已验证/已过期记录不参与"最近一次发送时间"判定。



## 修复说明



- **改动文件**：`backend/app/modules/open/services/sms_service.py`

- **方案**：重发节流查询去掉 `SmsCode.status == 0` 条件，仅按 `phone + purpose` 取 `created_at` 最新一条判定 60 秒间隔。

- **验证**：`backend/tests/open/test_sms.py` — TC-OPN-SMS-010 通过（已消费记录仍触发节流）。
