# 操作日志

> **所属阶段**：阶段二 - 运营后台完善
>
> **文档状态**：已完成
>
> **优先级**：高

## 一、功能概述

在 console 端新增"日志中心"模块，集中查看所有租户的操作日志。在 client 端所有写操作 API 上自动采集操作行为，异步双写到平台库和租户库，满足审计与问题排查需求。

## 二、业务背景

- 产品需要审计能力，记录每个租户的每个用户在系统内的操作行为
- 运营团队需要在 console 端集中查看和排查租户操作问题
- 租户自身也需要在企业端查看本企业内的操作记录

## 三、架构设计

### 3.1 双写架构

操作日志采用**双写**策略：

- **平台库 `sys_operation_log`**（含 `tenant_code` 字段）：供 console 端集中查询，支持跨租户检索
- **租户库 `biz_operation_log`**：供企业端本地查看

### 3.2 采集方式

通过 `@operation_log` 装饰器自动采集，装饰在 client 端的写操作 API 上：

```python
@router.post("")
@operation_log(module="车辆管理", action="新增", description="新增车辆")
async def create_vehicle(request: Request, ...):
    ...
```

装饰器职责：
- 从 `request.state` 获取当前用户和租户信息（由 `TenantMiddleware` 注入）
- 从 kwargs 中提取 Pydantic body 模型作为请求参数
- 计算接口耗时
- 捕获成功/失败状态
- 使用 `asyncio.create_task` 异步写入，不阻塞业务响应
- 写入使用独立 session，不影响业务事务

### 3.3 技术栈

- 日志库：沿用 loguru（仅在写入失败时记录错误日志）
- 装饰器：`app/common/operation_log.py`
- ORM：SQLAlchemy 2.0 + AsyncSession

## 四、数据模型设计

### 4.1 平台库 - sys_operation_log

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| user_id | int | 操作用户ID |
| username | varchar(50) | 操作用户名（手机号） |
| tenant_code | varchar(32) | 租户编码 |
| module | varchar(50) | 操作模块 |
| action | varchar(50) | 操作类型（新增/编辑/删除等） |
| description | varchar(255) | 操作描述 |
| request_method | varchar(10) | 请求方法 |
| request_url | varchar(255) | 请求URL |
| request_body | text | 请求参数（JSON，截断至2000字符） |
| response_body | text | 响应结果（JSON，截断至2000字符） |
| ip | varchar(50) | IP地址 |
| elapsed_time | int | 耗时（毫秒） |
| status | smallint | 状态 0-失败 1-成功 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |
| is_deleted | smallint | 是否删除 |

### 4.2 租户库 - biz_operation_log

与平台库结构相同，但不含 `tenant_code` 字段。

## 七、菜单配置

通过 `scripts/seed_log_center_menus.py` 脚本写入：

- 目录：日志中心（`/log-center`，sort_order=15）
- 子菜单：操作日志（`/log-center/operation-log`）

## 八、注意事项

- 装饰器日志写入是 fire-and-forget，写入失败不影响业务
- `request_body` 和 `response_body` 截断至 2000 字符
- GET 查询请求不记录（仅记录 POST/PUT/DELETE 写操作）
- 日志记录使用独立 DB session，不与业务事务混用
