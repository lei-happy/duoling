## 一、文档定位与业务背景

### 1.1 要解决的真实场景

一个物流企业（租户）在实际经营中，往往不是"一个法人干到底"，而是存在**多个经营主体**：

1. 集团下有**多个法人公司 / 分公司 / 车队**，各自独立核算、独立开票、独立对公结算；
2. 一辆车、一名司机、一条运力，在业务与财务上**必须归属到某个具体经营主体**（谁的车、挂在谁名下、运费走谁的账、开票抬头是谁）；
3. 财务对账、司机资金往来、开票，都需要按**经营主体**这个维度切分，否则多主体的钱会混在一起，无法分主体核算。

当前系统**缺失"经营主体"这一主数据**：

- `biz_driver` / `biz_vehicle` / `biz_capacity` 均**无 `enterprise_id`**，运力/车辆/司机无法归属主体；
- 仅 `biz_driver_account` / `biz_driver_fund_account` 预留了 `enterprise_id`，但**无主数据来源**、手工填写、未贯通；
- 财务费用单、任务单也无主体维度，无法分主体对账。

本模块提供一套**经营主体（法人经营主体）主数据**，并把它作为**运力资源与财务账务的归属维度**贯通到各业务实体。

**核心目标：让"车、人、运力、任务、钱"都能明确归属到某个经营主体，支撑多主体独立经营与分主体对账。**

### 1.2 与"组织架构"的区别（重要）

系统已存在 [`biz_department`](01.基础模块-组织架构与权限.md)（组织架构/部门树），它**不是本模块的经营主体**。二者概念相关但定位不同，本模块**新建独立表**，不改动、不复用它：

| 维度 | 既有 `biz_department`（组织架构） | 本模块 `biz_business_entity`（经营主体） |
|------|----------------------------------|------------------------------------------|
| 本质 | 企业内部的**人员/权限层级**（总部-分公司-部门-小组） | 独立核算的**法人/经营主体**（工商登记实体） |
| 关键属性 | `parent_id` 树形、`dept_type`、负责人 | 统一社会信用代码、法定代表人、对公账户、开票信息 |
| 关联对象 | `biz_user`（员工归属部门） | 运力 / 车辆 / 司机 / 任务 / 财务单据（业务与账务归属） |
| 层级 | 无限层级树 | 平铺列表（一期不做层级；可选关联到组织节点，远期） |
| 用途 | 控制人看哪些菜单、管哪些人 | 决定业务/资金归属、分主体对账、开票抬头 |
| 管理者 | 企业管理员（HR/权限视角） | 企业管理员（财务/工商视角） |

> 术语约定：下文"主体""经营主体"一律指本模块的 `biz_business_entity`；提到人员层级时明确写"组织架构 / 部门"。

### 1.3 与"租户"的关系

- **租户（tenant）= 一个客户企业**，对应一个独立业务库 `zt_biz_{tenant_code}`，数据物理隔离；
- **经营主体（enterprise）= 租户内部的多个法人核算单元**，同库内通过 `enterprise_id` 逻辑区分；
- 一个租户下 **1 ~ N 个**经营主体；单主体企业也至少有 1 个（内置默认主体）。

## 二、核心概念与边界

### 2.1 主体归属规则

| 业务实体 | 归属主体的含义 | 归属确定方式 |
|----------|----------------|--------------|
| 车辆 `biz_vehicle` | 车辆的产权/挂靠主体 | 新增/编辑车辆时选择 |
| 司机 `biz_driver` | 司机的用工/结算主体 | 新增/编辑司机时选择 |
| 运力 `biz_capacity` | 运力（人+车）的经营主体 | 由绑定的司机/车辆主体推导，或显式指定 |
| 任务 `biz_task` | 任务由哪个主体承运/核算 | 建单时选择（默认取运力主体） |
| 费用单 `biz_task_finance_doc` | 该笔收付归属主体 | **继承所属任务的 `enterprise_id`** |
| 资金账户 `biz_driver_fund_account` | 司机 × 主体唯一一账 | 由记账上下文的 `enterprise_id` 决定 |

### 2.2 一致性约束（本期为软约束，见 §5）

- 运力的主体，与其绑定司机、车辆的主体**应一致**；不一致时一期仅告警提示，不强制拦截（存量数据平滑）。
- 费用单主体**强制继承任务主体**，不单独选择，避免账/单主体错配。

## 三、数据模型

### 3.1 新增主表 `biz_business_entity`（经营主体）

`__table_tier__ = "core"`（注册租户即建表，并内置一个默认主体）。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | BigInt | PK | 主键（即各业务表引用的 `enterprise_id`） |
| `entity_code` | VARCHAR(50) | UNIQUE, NOT NULL | 主体编码（业务唯一标识，系统或人工生成） |
| `entity_name` | VARCHAR(100) | NOT NULL | 主体名称（法人全称） |
| `short_name` | VARCHAR(50) | NULL | 简称（列表/选择器展示用） |
| `unified_credit_code` | VARCHAR(30) | NULL | 统一社会信用代码 |
| `legal_person` | VARCHAR(50) | NULL | 法定代表人 |
| `registered_address` | VARCHAR(255) | NULL | 注册地址 |
| `contact_person` | VARCHAR(50) | NULL | 联系人 |
| `contact_phone` | VARCHAR(20) | NULL | 联系电话 |
| `bank_name` | VARCHAR(100) | NULL | 对公开户行（财务/对账用） |
| `bank_account` | VARCHAR(50) | NULL | 对公账号（财务/对账用） |
| `invoice_title` | VARCHAR(100) | NULL | 开票抬头（默认取 `entity_name`） |
| `invoice_tax_no` | VARCHAR(30) | NULL | 开票税号（默认取 `unified_credit_code`） |
| `is_default` | SmallInt | default 0 | 是否默认主体（1-是，租户内唯一） |
| `status` | SmallInt | default 1 | 状态 1-正常 0-停用（停用后不可被新业务选择） |
| `sort_order` | SmallInt | default 0 | 排序号 |
| `remark` | Text | NULL | 备注 |
| `created_at / updated_at / is_deleted` | — | — | 基类通用字段 |

- 唯一约束：`uk_be_code (entity_code)`；`is_default` 由服务保证租户内至多一条为 1。
- 内置默认主体：租户初始化时创建一条 `is_default=1` 的默认主体（名称可后续由客户改为真实法人名）。

### 3.2 各业务表新增关联字段 `enterprise_id`

统一新增 `enterprise_id BigInt NULL, index`，**一期可空**（见 §5.1 迁移策略）：

| 表 | 变更 | 说明 |
|----|------|------|
| `biz_driver` | 新增 `enterprise_id` | 司机归属主体 |
| `biz_vehicle` | 新增 `enterprise_id` | 车辆归属主体 |
| `biz_capacity` | 新增 `enterprise_id` | 运力归属主体（可由人/车推导） |
| `biz_task` | 新增 `enterprise_id` | 任务承运/核算主体 |
| `biz_task_finance_doc` | 新增 `enterprise_id` | 费用单归属主体（继承任务） |
| `biz_driver_fund_account` | **已存在** `enterprise_id` | 本期真正贯通：账户唯一键改由 `(driver_id, enterprise_id)` 生效 |
| `biz_driver_fund_transaction` | **已存在** `enterprise_id` | 冗余，随账户 |
| `biz_driver_account`（收款账户） | **已存在** `enterprise_id` | 由手填改为主体选择器选择 |

> 社会运力 `biz_social_capacity_*`、承运商运力 `biz_carrier_capacity_*` 是否纳入主体归属，列为**远期**（本期聚焦自有运力）。

## 五、业务规则与一致性

### 5.1 迁移策略（一期可空、平滑迁移）

| 规则 | 说明 |
|------|------|
| 字段可空 | 各业务表 `enterprise_id` 一期 `NULL`，存量数据不强制回填，避免大表阻塞与业务中断 |
| 新增引导 | 新增车辆/司机/运力/任务时，主体选择器**默认选中默认主体**，引导逐步补全 |
| 默认主体 | 租户内置 1 个默认主体（`is_default=1`）；未选择主体的新数据可落默认主体或留空（按表单默认） |
| 后期收紧 | 待存量数据补齐后，独立需求将 `enterprise_id` 改为必填并加非空约束 |

### 5.2 主体管理规则

| 规则 | 说明 |
|------|------|
| 默认主体唯一 | 设为默认时，自动取消原默认主体的 `is_default`；至少保留 1 个正常主体为默认 |
| 停用限制 | 停用的主体不可被新业务选择；已归属的存量数据不受影响（仅不可新选） |
| 删除校验 | 存在关联业务（司机/车辆/运力/任务/费用单/资金账户）时**禁止删除**，提示"该主体下存在关联数据，无法删除"；默认主体不可删除 |
| 编码唯一 | `entity_code` 租户内唯一，编辑时不可修改 |

### 5.3 归属与隔离规则

| 规则 | 说明 |
|------|------|
| 费用单继承任务主体 | 费用单 `enterprise_id` 从所属任务继承，不单独选择 |
| 资金账户按主体定位 | `DriverFundAccountService._get_or_create` 改为按 `(driver_id, enterprise_id)` 查询/创建；唯一键 `uk_dfa_driver_ent` 生效 |
| 联动透传 | `DriverFundOrchestrator` 由费用单 `doc.enterprise_id` 透传主体，替换现有硬编码 `enterprise_id=None` |
| 运力一致性 | 运力主体与其司机/车辆主体不一致时，一期仅前端/服务告警，不拦截 |

## 九、数据库迁移

主表新增整表（core tier，注册库 runner 自动建表 + 内置默认主体）；关联字段为存量表加列，走 versioned migration。

1. 新增 ORM 模型 `biz_business_entity`（`__table_tier__ = "core"`）；
2. 为 `biz_driver / biz_vehicle / biz_capacity / biz_task / biz_task_finance_doc` 增加可空 `enterprise_id` 列 + 索引，编写 versioned migration（加列幂等，参照 `20260706_001_driver_fund_account.py` 的 `_col_exists` 守卫风格）；
3. `python -m scripts.migration.autogen tenant --name "business_entity"` 刷新 `snapshots/tenant_schema.json`；
4. 把 `biz_business_entity` 加入相应 feature 的 `required_tables`（platform_sync），并新增经营主体菜单快照；
5. `python -m scripts.migration.check` 确认无 drift；
6. 租户初始化钩子：创建默认主体（`is_default=1`）。

遵循 [database-migration 规范](../../../../backend/scripts/migration/README.md)。

## 十一、测试要点

| # | 场景 | 期望 |
|---|------|------|
| 1 | 新建/编辑主体 | 编码唯一校验、开票信息默认回填 |
| 2 | 设为默认主体 | 原默认自动取消，租户内唯一默认 |

| 4 | 删除有关联数据的主体 | 拦截提示，禁止删除 |
| 5 | 删除默认主体 | 拦截提示 |
