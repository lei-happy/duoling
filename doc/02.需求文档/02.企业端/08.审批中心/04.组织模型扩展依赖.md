## 一、为什么需要扩展

审批中心的审批人类型里，"指定成员 / 指定角色 / 指定部门 / 发起人自选"依赖的组织数据**当前已具备**；但"**部门负责人**"和"**逐级上级主管**"两类动态审批人，依赖目前**缺失**的组织数据：

| 审批人类型 | 需要的数据 | 当前现状 | 缺口 |
|-----------|-----------|---------|------|
| 部门负责人 | 部门 → 负责人的 user_id | `biz_department.leader` 仅为**文本姓名** | 无法可靠映射到具体用户 |
| 逐级上级主管 | 用户 → 直属上级的 user_id（汇报线） | **不存在**任何 `supervisor` / `manager` 字段 | 完全缺失 |
| 发起人所属部门（解析上述两者的起点） | 登录上下文含部门 | `/auth/user-info` **不返回**部门 | 需补充 |

> 因此本扩展是审批中心"动态审批人"能力的**前置依赖**，落在第 2 期。第 1 期前端可保存这两类配置但解析回退到 `empty_strategy`，并在 UI 标注"第 2 期生效"。

## 二、扩展设计

### 2.1 部门表加"负责人用户ID"

`biz_department`（`backend/app/modules/client/models/organization/biz_department.py`）新增：

| 字段 | 类型 | 说明 |
|------|------|------|
| `leader_user_id` | BigInt nullable | 部门负责人的 `biz_user.id`；可空（未设置） |

- **保留**原 `leader VARCHAR(50)` 文本字段（兼容旧数据与纯展示场景），新增 `leader_user_id` 作为可解析的结构化字段。
- 前端组织管理编辑页（`enterprise/organization/components/organization-edit.vue`）增加"部门负责人"选择项（`UserSelect`，可限定为本部门成员），写入 `leader_user_id`，同时把姓名冗余回 `leader` 文本以便列表展示。

### 2.2 用户表加"直属上级"

`biz_user`（`backend/app/modules/client/models/user/biz_user.py`）新增：

| 字段 | 类型 | 说明 |
|------|------|------|
| `supervisor_user_id` | BigInt nullable | 直属上级的 `biz_user.id`；可空（如总经理无上级） |

- 形成**汇报线**：员工 → 直属上级 → 上级的上级……支撑"逐级上级第 N 级"解析。
- 前端员工编辑页（`enterprise/user/components/user-edit.vue`）增加"直属上级"选择项（`UserSelect`）。
- **防环**：设置时校验不能选自己、不能形成环（A→B→A）；解析时也限制最大上溯层级（如 ≤ 10）兜底。

### 2.3 登录上下文返回部门

`/auth/user-info`（`UserInfoOut`，`backend/app/modules/console/schemas/auth/auth.py` + `AuthService.get_user_info`）补充返回：

| 字段 | 来源 |
|------|------|
| `organizationId` | `biz_user.department_id` |
| `organizationName` | 关联 `biz_department.dept_name` |

> 前端 `User` 接口（`src/store/modules/user.ts`）已声明 `organizationId`，当前运行时为 `undefined`；本扩展使其真正有值。审批提交时把发起人部门作为 `initiator_dept_id` 传给引擎（01 §2.4），用于"发起人所在部门负责人"与上级解析的起点。

## 三、解析算法

### 3.1 部门负责人

```python
async def _dept_leader_user(db, dept_id: int) -> list[int]:
    dept = await get_department(db, dept_id)
    if dept and dept.leader_user_id:
        return [dept.leader_user_id]
    # 可选回退：沿 parent_id 向上找最近一个有 leader 的父部门
    return []   # 空 → 走节点 empty_strategy
```

可配置回退策略：本部门未设负责人时，是否向上找父部门负责人（推荐开启，避免空审批人）。

### 3.2 逐级上级主管

```python
async def _supervisor_chain(db, user_id: int, level: int) -> list[int]:
    cur = user_id
    for _ in range(level):
        u = await get_user(db, cur)
        if not u or not u.supervisor_user_id:
            return []          # 链路断了 → 空 → empty_strategy
        cur = u.supervisor_user_id
    return [cur]
```

- `level=1` = 直属上级；`level=2` = 上级的上级，以此类推。
- 防环 + 最大层级保护，避免死循环。

```mermaid
flowchart LR
    Emp["发起人 张三"] -->|supervisor| L1["李四 组长 level1"]
    L1 -->|supervisor| L2["王五 部门经理 level2"]
    L2 -->|supervisor| L3["赵六 总监 level3"]
```

## 四、兼容策略

| 议题 | 策略 |
|------|------|
| 旧 `leader` 文本字段 | **保留不删**；展示用文本，解析用 `leader_user_id`；两者不强制一致 |
| 存量部门无 `leader_user_id` | 可空；解析回退到父部门或 `empty_strategy`，不阻断 |
| 存量用户无 `supervisor_user_id` | 可空；逐级上级解析遇空即返回空，走 `empty_strategy` |
| 老租户库无新列 | 由迁移按需补列（见 §五）；列均可空，无回填阻塞 |
| `user-info` 老前端 | 新增字段为增量，老前端忽略不影响 |

## 五、迁移要点（属"改现有表加列"）

> 注意：这与审批引擎"新增表"不同——加列**必须走 versioned migration**（详见 [05.实施方案与部署落地](05.实施方案与部署落地.md) 与 [migration/README.md](../../../../backend/scripts/migration/README.md)）。

1. 改 ORM：`biz_department` 加 `leader_user_id`、`biz_user` 加 `supervisor_user_id`（**均 nullable，不设 NOT NULL**，规避线上存量数据 ALTER 失败）。
2. `cd backend && make migrate-check` → 有 drift。
3. `make migrate-new-tenant name="add org approver fields"` 生成租户库迁移 + 自动刷 `tenant_schema.json`。
4. 人工 review：确认可空、无需回填、无类型截断、新增列不带唯一约束。
5. `make migrate-apply-local` 本地验证。
6. 一并提交：ORM 文件 + `scripts/migration/versions/<new>.py` + `snapshots/tenant_schema.json`。
7. （可选）老租户回填脚本放 `scripts/fix/`：把 `leader` 文本按姓名模糊匹配 `biz_user.real_name` 写入 `leader_user_id`，**匹配不到留空**，匹配到多个不写（人工确认），脚本幂等。

> `/auth/user-info` 的改动只涉及 schema/service，不动表结构，无需迁移。

## 六、分期落地标注

| 能力 | 期次 | 依赖 |
|------|------|------|
| 指定成员 / 角色 / 部门 / 发起人自选 | **第 1 期**（无需本扩展） | 现有组织数据 |
| 流程配置 UI 可保存"部门负责人 / 逐级上级"配置 | 第 1/3 期 | 仅前端，解析回退 |
| 部门负责人解析生效 | **第 2 期** | `leader_user_id` + 组织页维护入口 |
| 逐级上级解析生效 | **第 2 期** | `supervisor_user_id` + 员工页维护入口 |
| `user-info` 返回部门 | **第 2 期** | schema/service 改造 |
