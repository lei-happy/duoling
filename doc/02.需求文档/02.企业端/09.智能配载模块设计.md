# 智能配载模块设计与落地方案

> 版本：v1.0（首版落地）
> 定位：**专业版（pro）** 亮点功能，`feature_code = smart_stowage`
> 关联：智能配载之后接续「智能调度」（`smart_dispatch`，见文末衔接章节）

---

## 1. 背景与目标

### 1.1 术语对齐

| UI 术语 | 领域实体 | 说明 |
|---------|---------|------|
| 配载单 / 配载建单 | `biz_task` 运输任务单 | 一个任务 = 一组商品车 + 承运 + 线路 |
| 商品车 | `biz_waybill_cargo` 运单货物明细 | 通过 `biz_task_waybill_item` 按台数挂接到任务 |
| 智能配载 | 本模块 | 用算法自动推荐「哪几台商品车组成一个配载单」 |

### 1.2 现状

创建配载单目前是**纯人工**流程：调度员在「配载建单」页从候选商品车池（`GET /business/task/candidate-waybills`）逐台勾选，提交 `POST /business/task`（`source=1`）。

### 1.3 目标

> **智能配载 = 从"待配商品车池"中，用算法自动推荐"哪几台商品车组成一个配载单"，使运力利用最优。**

本质是**带约束的线路聚类 + 装箱（Bin-Packing）**问题。产出若干「配载方案」，调度员一键采纳后复用现有建单链路落为任务（`source=2`）。

---

## 2. 约束与目标建模

### 2.1 硬约束（必须满足）

- **车位约束**：一个方案的商品车折算占位 ≤ 板车车位数（`biz_trailer_ext.parking_spots`）
- **方向一致性**：同一方案的商品车起终点应在同一条干线/同方向
- （V2）时间窗、客户拼车规则、车型混装规则

### 2.2 软目标（加权打分，择优排序）

| 目标 | 权重（V1 默认） | 说明 |
|------|----------------|------|
| 装载率最大化 | 0.7 | 折算占位 / 车位数，**核心指标** |
| 线路聚合度 | 0.2 | 同线聚合台数越多越好 |
| 客户集中度 | 0.1 | 客户数越少交付越简单 |

### 2.3 占位系数（关键数据）

商品车按车型折算车位占用：

```
方案占用车位 = Σ(商品车台数 × 车型占位系数)
```

V1 用一张**默认系数表**兜底（可按车型关键字命中），后续可迁移到数据字典/车型档案：

| 车型关键字 | 占位系数 |
|-----------|---------|
| 默认（轿车/未知） | 1.0 |
| SUV / MPV / 商务 | 1.2 |
| 皮卡 / 轻卡 / 大型 | 1.6 |

## 3. 算法设计（分层可演进）

采用「召回 → 分组 → 装箱 → 择优」四段式管线：

```
候选商品车池 + 板车车位档 + 占位系数
   │
   ├─ ① 召回/清洗：标准化起终点、折算占位
   ├─ ② 线路聚类：按 (origin, destination) 聚成候选簇
   ├─ ③ 装箱求解：簇内 FFD（首次适应递减）在车位约束下组包
   └─ ④ 多目标打分：装载率/聚合度/集中度加权 → Top-N 方案
```

| 阶段 | 算法 | 依赖 |
|------|------|------|
| **V1（本次）** | 规则 + 贪心 FFD + 加权打分 | 纯 Python，无外部依赖，可解释 |
| V2 | 模拟退火 / 遗传算法全局寻优 | — |
| V3（可选） | OR-Tools 约束求解 / LLM 处理软规则 | 外部依赖 |

**关键**：算法层（`SmartStowageEngine`）为纯函数、不碰 DB（对齐 `carrier_freight_matcher`），内部算法可无痛替换。

## 4. 系统架构与接入方式

完全复用现有 `carrier_freight` 的「**纯算法层 + 编排层 + 任务表 + 异步 worker**」范式。

```
前端 智能配载工作台 (hasFeature('smart_stowage'))
   │  POST /business/smart-stowage/generate
   ▼
API 层 (require_feature('smart_stowage'))
   │
   ▼
SmartStowageService 编排层
   ├─ 读候选：TaskWaybillItemService.list_candidate_cargoes
   ├─ 调算法：SmartStowageEngine.generate()  (纯算法)
   ├─ 落方案：biz_smart_stowage_plan / _plan_item
   └─ 采纳：TaskService.create_task(source=2)  ← 复用现有建单
   │
   ▼
biz_smart_stowage_task (生成任务表，认领模式)
   ▲
   └─ SmartStowageWorker (APScheduler 多租户轮询，供未来定时自动预配)
```

### 4.1 触发形态（本次：手动一键生成）

- 调度员在工作台设置筛选 →「一键生成方案」→ `POST /generate`
- **V1 同步执行**（池子可控 + 手动触发 + 算法快）：请求内 `生成任务(pending→running→success)` 并直接产出方案返回，秒级出结果，**无需 worker 常驻**
- 任务表 + worker 架构保留，未来切「待配池达阈值定时自动预配」零成本（worker 只认领 `pending`，与同步路径不冲突）

### 4.2 关键接入点：采纳即复用建单

方案采纳时**不重写建单逻辑**，把方案明细组装成 `TaskCreate(source=2)` 喂给现成 `TaskService.create_task`，下游调度/装卸/计费链路零改动，与人工配载产出物完全同构。

## 5. 数据模型（3 张租户表 `biz_*`，`__table_tier__="business"`）

新表走 `sys_product_feature.required_tables` 自动建表机制（runner Phase 1），**无需手写 versioned migration**，只需：注册 ORM 模型 + 把表名加入 `smart_stowage` feature 的 `required_tables` + 刷 ORM snapshot。

### 5.1 `biz_smart_stowage_task` 生成任务

| 字段 | 类型 | 说明 |
|------|------|------|
| status | varchar(32) | pending/running/success/failed |
| filter_json | text | 候选筛选条件快照 |
| params_json | text | 算法参数（targetSpots、权重、系数覆盖） |
| candidate_count | int | 参与计算的候选行数 |
| plan_count | int | 产出方案数 |
| adopted_count | int | 已采纳方案数 |
| triggered_by_user_id / _name | | 触发人 |
| retry_count / max_retry_count | int | worker 重试 |
| error_message | varchar(1000) | 失败原因 |
| started_at / finished_at | datetime | |

### 5.2 `biz_smart_stowage_plan` 方案

| 字段 | 说明 |
|------|------|
| plan_task_id | 关联生成任务 |
| plan_no | 方案序号 |
| origin / destination | 方案主线路 |
| vehicle_count | 商品车台数 |
| occupied_spots | 折算占用车位 |
| target_spots | 目标板车车位 |
| load_rate | 装载率（0-100） |
| customer_count / waybill_count | 客户数 / 运单数 |

| reason | 可解释理由 |
| status | 0待采纳 1已采纳 2已忽略 |

### 5.3 `biz_smart_stowage_plan_item` 方案明细

| 字段 | 说明 |
|------|------|
| plan_id | 关联方案 |
| waybill_id / waybill_cargo_id / quantity | 挂接三要素（可直接映射 `TaskWaybillItemIn`） |
| waybill_no / customer_name / vehicle_brand / vehicle_model / vin | 展示快照 |
| origin / destination | 起终点 |
| occupy_coefficient | 该行占位系数 |

## 6. API 设计（前缀 `/business/smart-stowage`，全量 `require_feature("smart_stowage")`）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/generate` | 生成配载方案（同步产出），返回 planTaskId + 方案概览 |
| GET | `/tasks/{id}` | 查生成任务状态与统计 |
| GET | `/plans` | 按 planTaskId 拉方案列表（含明细） |
| POST | `/plans/{id}/adopt` | 采纳方案 → 建任务（`source=2`），返回 taskId |
| POST | `/plans/{id}/ignore` | 忽略方案 |

## 7. 专业版门控落地

1. console 新建 feature `smart_stowage`（名称「智能配载」），`required_tables` 填 3 张新表
2. `version_feature` 中**仅 `pro` 勾选**（基础配载 `biz_task` 仍留 standard，实现分级）
3. 智能配载菜单 / 静态路由绑定；前端 `hasFeature('smart_stowage')` 控制入口
4. 所有智能配载 API 挂 `require_feature("smart_stowage")`
5. `python -m scripts.platform_sync export` 导出快照 → 给目标租户 `assign_product(pro)`

## 10. 智能调度衔接（下一阶段）

智能配载产出「待分配任务」，智能调度回答**"这单谁承运、走哪条线最优"**。

- 评分地基已有：`carrier_freight_matcher`（承运成本）、`cost_matcher`（自有成本）
- 智能调度 = 在成本评分之上扩展为多目标运力推荐（成本 + 承运商画像履约 + 线路匹配 + 运力可用性）
- 接入方式与智能配载完全对称：新增 `smart_dispatch` feature（pro）、`SmartDispatchEngine`（复用并扩展现有 matcher）、结果落地到现有 `assign-carrier` / `plan-route` 接口
