## 一、文档定位与要解决的问题

### 1.1 问题

财务模块此前只规划了「单据台账」，即每类单据一个列表页。台账是**按单据组织**的，而人是**按岗位工作**的，两者错位会产生三类日常摩擦：

| # | 摩擦 | 具体表现 |
|---|------|---------|
| 1 | 岗位要跨台账拼信息 | 出纳要付款，得依次打开任务费用单台账、承运商结算单、司机工资单三个页面，各自筛「已审批」状态，才知道今天要打多少笔 |
| 2 | 待办没有归集入口 | 对账专员不知道「哪些运单该进对账单了」「哪些对账单的快照已经和业务侧不一致了」，只能靠人记周期 |
| 3 | 权限粒度按页给，不按动作给 | 出纳为了能付款必须被授予结算单页面权限，一并拿到了改金额的能力，违背钱账分离 |

### 1.2 设计目标

| 目标 | 落地 |
|------|------|
| 每个岗位有唯一主入口 | 三个工作台：对账、出纳、票据。会计岗直接用台账层，不额外造台 |
| 工作台只做「筛待办 + 执行」，不做单据 CRUD | 避免与台账层功能重复实现，也避免两套校验逻辑漂移 |
| 权限按动作发，不按页面发 | 权限点拆到 `pay` / `receive` / `batch-pay` 等动作级，出纳不拿 `edit` |
| 钱账分离可落地 | 制单（会计）、审批（主管）、付款（出纳）三个动作的权限点互斥授予 |

### 1.3 明确不做

| 不做 | 原因 |
|------|------|
| 为应收会计 / 应付会计单独建工作台 | 他们的工作对象就是自己那几张台账，台账页顶部的统计卡 + 状态 Tab 已够用；再加一层只是多一次跳转 |
| 工作台里做单据编辑 | 校验逻辑会与台账层重复，长期必然漂移 |
| 岗位 = 系统角色写死在代码里 | 岗位是运营配置概念，落地为 `sys_role` + `sys_role_menu` 授权，代码不预设分配（见 §五） |

## 二、五个岗位的职责边界

### 2.1 职责矩阵

| 岗位 | 核心职责 | 主入口 | 可写对象 | 明确不给 |
|------|---------|--------|---------|---------|
| **应收会计** | 客户对账制单、结算单制单、开票申请、催收跟踪 | 客户对账单台账 | 客户对账单、客户结算单、销项发票（草稿态） | 审批权、收款登记权 |
| **应付会计** | 承运商对账制单、司机工资核算、任务费用单复核、进项票登记 | 承运商对账单台账 | 承运商对账单、承运商结算单、司机工资单、进项发票、任务费用单 | 审批权、付款权 |
| **对账专员** | 上下游对账事项核对、运输单与财务单一致性检查、差异登记与协商 | 对账工作台 | 对账行的 `adjust_amount`、差异记录 `biz_recon_diff` | 结算单与发票的任何写权限 |
| **出纳** | 银行付款执行、到账认领、账户余额维护 | 出纳工作台 | 打款批次、收款单、银行账户、单据的 `pay` / `receive` 动作 | 任何单据的 `create` / `edit` / `delete` / `approve` |
| **财务主管** | 单据审批、撤销支付、解锁、差异强制确认、经营核算查看 | 各台账 + 经营核算 | 审批与高权限动作 | 不限制（但审批自己制的单应由流程约束，见 §2.3） |

### 2.2 岗位与单据的读写矩阵

行为码含义：`R` 只读、`C` 建单、`E` 编辑草稿、`S` 提交、`A` 审批、`P` 付款/收款、`X` 高权限（撤销支付/解锁/强制撤销）。

| 单据 | 应收会计 | 应付会计 | 对账专员 | 出纳 | 财务主管 |
|------|:-------:|:-------:|:-------:|:----:|:-------:|
| 客户对账单 | C E S | R | R + 调整行 | R | A X |
| 客户结算单 | C E S | R | R | P | A X |
| 销项发票 | C E S | R | — | R | A X |
| 承运商对账单 | R | C E S | R + 调整行 | R | A X |
| 承运商结算单 | R | C E S | R | P | A X |
| 进项发票 | R | C E S | R | R | A X |
| 司机工资单 | — | C E S | R | P | A X |
| 任务费用单 | R | C E S | R | P | A X |
| 收款单 | R | — | R | C E P | A X |
| 打款批次 | — | R | — | C E S P | A X |
| 银行账户 | R | R | — | C E | R |
| 应收账龄 | R | — | R | R | R |
| 经营核算 | R | R | — | — | R |

> 「对账专员」对所有对账单都只有「读 + 调整行」，没有 `S 提交确认`。这是刻意的：对账事项的最终确认权归制单会计，专员的产出是「核对结论与差异记录」，避免核对者自己拍板。若某企业人手少要合并岗位，运营侧把两个角色的权限点一起授给同一用户即可，系统不阻止。

### 2.3 钱账分离的落地方式

三组权限点应互斥授予，同一用户不应同时持有：

| 组 | 权限点 | 持有者 |
|---|--------|-------|
| 制单组 | `create` / `edit` / `delete` / `submit` | 应收会计、应付会计 |
| 审批组 | `approve` / `reject` / `withdraw` | 财务主管 |
| 出款组 | `pay` / `receive` / `batch-pay` / `claim-receipt` | 出纳 |

系统层面**不硬性拦截**同一用户被授予多组权限（小微企业确实一人多岗），但要在两处提示：

1. 角色配置页：勾选跨组权限点时给出「该角色同时具备制单与付款权限，不满足钱账分离」的软提示；
2. 单据详情页：若当前操作人与 `created_by` 相同且正在执行 `approve`，提示「您正在审批自己创建的单据」，仍允许执行但写入 `biz_finance_doc_event.reason` 备注。

> 硬拦截会让 3 人财务团队的企业无法开工，收益不抵成本。审计诉求用「留痕 + 提示」满足。

## 三、三个工作台的信息架构

### 3.1 通用规范

三个工作台共享同一套页面骨架，避免各写一套：

| 区块 | 规范 |
|------|------|
| 顶部 KPI 卡 | 4~5 个统计块，每块可点击，点击即把下方列表筛到该口径（与现有「费用工作台」`views/operation/task-finance-workbench` 的交互一致） |
| 状态池 Tab | 按待办阶段分 Tab，每个 Tab 带数字角标；Tab 切换只改筛选条件，不换页面 |
| 主列表 | `ele-pro-table`，支持多选 + 批量动作；行内动作只保留该岗位的执行动作 |
| 批量动作条 | 选中行后浮出，展示「已选 N 笔 / 合计金额」+ 该岗位的批量按钮 |
| 跳转出口 | 任一行可跳到对应单据台账的详情抽屉做完整操作，工作台自身不承载 CRUD |

> 复用既有实现：「费用工作台」已经是这套结构的一个实例。第 2 期落地对账工作台时只抽出了 KPI 卡组件 `<finance-kpi-cards>`（`views/finance/components/`），Tab 与列表没有插槽化——四个 Tab 的行结构差得太远（候选池是客户聚合、差异待办是跨单据、待重核与待回签是对账单台账行），硬套一层插槽只会把 `v-if` 从页面搬进骨架。第 3、4 期再上两个工作台时若出现真正重复的结构，再回来抽。

### 3.2 对账工作台 `/finance/recon-workbench`

**服务岗位**：对账专员。**期次**：第 2 期（先只上客户侧，第 3 期补承运商侧）。**状态**：✅ 已落地。

落地实现：读聚合在 `services/finance/recon/workbench_service.py`（KPI 与 Tab 计数一次返回），API 在 `api/finance/recon_workbench.py`（3 个只读路由），页面 `views/finance/recon-workbench/index.vue`。工作台确实不含 CRUD——建单弹窗与差异处置弹窗直接复用客户对账单页的组件，写操作走的仍是对账单台账的接口。「待对账任务」卡与承运商侧留到第 3 期。

#### KPI 卡

| 卡 | 口径 |
|---|------|
| 待对账运单 | `waybill.status=5` 且未挂入任何非撤销对账单的运单数（按客户分组可下钻） |
| 待对账任务 | `task.status=5` 且 `is_recon_bound=0` 且未进任务级结算单的任务数（第 3 期） |
| 待重核对账单 | 存在 `recon_dirty=1` 对账行的对账单数（见 `09`） |
| 未处置差异 | `biz_recon_diff.status=0` 的差异条数 + 差异金额合计 |
| 本期已确认 | 当月 `status=2 已确认` 的对账单数与金额 |

#### 状态池 Tab

| Tab | 内容 | 岗位动作 |
|-----|------|---------|
| 候选池 | 可纳入对账的运单 / 任务候选（来自 `linkage` 候选池） | 勾选后「生成对账单」，跳到台账新建页 |
| 待重核 | 有脏标记的对账行 | 「重新核对」触发一致性核对，展示差异对比 |
| 差异待办 | 未处置差异 | 「回灌重算」/「登记差异」/ 提请强制确认 |
| 待客户回签 | `status=2` 且 `confirmed_by_customer_at` 为空 | 「上传回签」 |

#### 与 09 的关系

工作台是一致性核对器的**唯一 UI 入口**。核对规则、差异分类、处置路径全部在 `09` 定义，工作台只负责呈现与触发。

### 3.3 出纳工作台 `/finance/cashier-workbench`

**服务岗位**：出纳。**期次**：第 4 期。

#### KPI 卡

| 卡 | 口径 |
|---|------|
| 待付笔数 / 金额 | 全部 `status=2 已审批` 的应付单据（任务费用单 + 承运商结算单 + 司机工资单）笔数与合计 |
| 今日已付 | 当日 `paid_at` 落在今天的应付单据金额合计 |
| 待认领到账 | `receipt_voucher.status=0` 或核销未满额的收款单 |
| 账户可用余额 | `biz_bank_account` 各账户余额合计（按经营主体分组下钻） |
| 批次执行异常 | `payment_batch.status=6 部分失败` 的批次数 |

#### 状态池 Tab

| Tab | 内容 | 岗位动作 |
|-----|------|---------|
| 待付款 | 已审批未付的应付单据，跨三类单据统一视图 | 勾选「加入打款批次」→ 选付款账户 → 提交批次 |
| 我的批次 | 本人创建的打款批次 | 「执行」/「登记结果」/「重试失败笔」 |
| 待认领到账 | 银行到账但未核销完的收款单 | 「登记收款单」/「核销到结算单」 |
| 已收款 | 近 30 天已收款结算单 | 只读，供核对 |

#### 关键约束

出纳工作台的「待付款」Tab 是**跨单据聚合视图**，实现上是三条 UNION 查询而非新表。列表行必须带 `doc_kind` 以便跳转到正确台账。批次与核销的完整规则见 `10`。

### 3.4 票据工作台 `/finance/invoice-workbench`

**服务岗位**：应收会计（销项）+ 应付会计（进项）。**期次**：第 4 期。

#### KPI 卡

| 卡 | 口径 |
|---|------|
| 待开票 | `customer_settlement.invoice_required=1` 且 `invoice_amount_total < actual_amount` 的结算单数与差额 |
| 开票中 | 销项发票 `status=1 申请中` 的张数与金额 |
| 待收票 | 承运商结算单已支付但 `invoice_matched=0` 的单数与金额（进项票缺口） |
| 票款不符 | 进项票核销金额与结算单金额不一致的条数（见 `11` §四） |
| 本月票量 | 本月销项已开 / 进项已收的张数与金额 |

#### 状态池 Tab

| Tab | 内容 | 岗位动作 |
|-----|------|---------|
| 待开票（销项） | 需开票的结算单 | 勾选「申请开票」，支持拆票与合并开票 |
| 开票中（销项） | 申请中的发票 | 「录入发票号完成开票」/「退回修改」 |
| 待收票（进项） | 缺进项票的承运商结算单 | 「登记进项票」 |
| 票款不符 | 金额不一致的核销关系 | 「调整核销金额」/「登记差异」 |

### 4.2 工作台权限点（`menu_type=1`）

工作台**不含** `create` / `edit` / `delete`，只有 `list` + 岗位执行动作：

```text
finance:recon-wb:list                 查询（进入工作台）
finance:recon-wb:recheck              触发一致性重新核对
finance:recon-wb:raise-diff           登记差异
finance:recon-wb:recalc               触发计费引擎回灌重算
finance:recon-wb:gen-recon            从候选池生成对账单（跳转带参，实际建单权限仍校验台账的 create）

finance:cashier-wb:list               查询
finance:cashier-wb:batch-pay          批量打款（创建并执行打款批次）
finance:cashier-wb:claim-receipt      到账认领
finance:cashier-wb:retry-failed       重试批次失败笔

finance:invoice-wb:list               查询
finance:invoice-wb:apply-invoice      申请开票（销项）
finance:invoice-wb:register-invoice   登记进项票
finance:invoice-wb:match              票款核对/调整核销金额
```

> `gen-recon` 只放行「跳转 + 带参」，真正落库仍走 `finance:cust-recon:create` 校验。避免通过工作台绕过台账层权限。

| `finance:cust-settle:edit` | √ | — | √ |
| `finance:cust-settle:submit` | √ | — | √ |
| `finance:cust-settle:approve` | — | — | √ |
| `finance:cust-settle:reject` | — | — | √ |

## 五、角色配置约定

### 5.1 不在代码里预设角色

按 [deploy-migration-guard](../../../../.cursor/rules/deploy-migration-guard.mdc) 的约定，菜单入库后：

- 租户管理员（`sys_user_tenant.user_type=1`）与超管走全量菜单，入库即可见；
- 其余角色需要 `sys_role_menu` 授权，属**运营配置**，不在代码或 seed 里擅自分配。

因此本文的岗位是**推荐配置模板**，落地时由运营/实施在租户端「角色管理」按 §4.3 的粒度勾选。

### 5.2 推荐角色模板

供实施参考，可直接照抄成 5 个角色：

| 角色名 | 授权范围 |
|-------|---------|
| 应收会计 | 客户对账单、客户结算单、销项发票、应收账龄的 `list/detail/create/edit/submit/export`；票据工作台 `list/apply-invoice` |
| 应付会计 | 承运商对账单、承运商结算单、司机工资单、进项发票、费用单台账的 `list/detail/create/edit/submit/export`；票据工作台 `list/register-invoice` |
| 对账专员 | 对账工作台全部动作；各对账单的 `list/detail/export` + 行调整 |
| 出纳 | 出纳工作台全部动作；各结算单/工资单/费用单的 `list/detail/pay|receive/export`；银行账户 `list/detail/create/edit` |
| 财务主管 | 全部台账的 `approve/reject/withdraw/cancel-receive/cancel-payment/force-cancel/unlock`；经营核算 `list/export` |

## 六、前端实现要点

| 项 | 要求 |
|---|------|
| 通用骨架组件 | 只抽 KPI 卡：`views/finance/components/finance-kpi-cards.vue`（已落地，见下方说明）。Tab + 表格不做插槽化 |
| KPI 卡接口 | 每个工作台一个 `GET /api/client/finance/<wb>/summary`，返回全部卡片数值，避免前端并发多个统计请求 |
| Tab 计数 | 与 KPI 同一接口返回，不单独请求 |
| 批量动作的部分失败 | 统一返回 `{ successCount, failCount, failures: [{ id, docNo, message }] }`，前端用可展开的结果弹窗呈现，不用 toast 吞掉失败明细 |
| 权限控制 | 按钮级 `hasPermission('finance:cashier-wb:batch-pay')`，与既有页面写法一致 |
| 提示语 | 遵循 [humanized-ux-copy](../../../../.cursor/rules/humanized-ux-copy.mdc)：如「正在批量打款，请稍候…」「已成功打款 12 笔，3 笔未成功，请查看失败原因」 |

## 七、测试要点

1. **工作台无 CRUD**：直接 POST 工作台路径下的建单接口 → 404（工作台不暴露建单接口）
2. **权限绕过**：仅持 `recon-wb:gen-recon` 的用户调用对账单 create → 403
3. **出纳无编辑权**：仅持出纳权限点的用户 PUT 客户结算单 → 403
4. **KPI 与列表口径一致**：点击「待付笔数」卡后列表条数 = 卡片数值
5. **跨单据聚合正确**：出纳工作台「待付款」笔数 = 三类应付单据 `status=2` 之和
6. **批量部分失败**：构造 1 笔金额超账户余额，批量打款返回 `failCount=1` 且成功笔已置 3、失败笔仍为 2
7. **自审提示**：`created_by` = 当前用户时执行 approve，事件表 `reason` 含自审备注
8. **跨组权限软提示**：角色同时勾选 `create` 与 `pay` → 配置页出现钱账分离提示且允许保存
