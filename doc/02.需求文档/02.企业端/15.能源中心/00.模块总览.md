## 一、模块定位

能源中心是租户端**一级模块**，统一管理物流企业付给能源供应商的油 / 气 / 电资金与消费流水。它回答三件事：

| 经营问题 | 落点 |
|---------|------|
| 钱在哪、还剩多少、会不会沉淀 | 能源账户 + 每日余额快照 + 资金效率指标 |
| 加在哪辆车、哪个司机、哪次任务 | 消费台账 + 卡绑定历史匹配 |
| 和供应商账单对不对、有没有异常加注 | 对账 + 风控异常池 |

一句话：**能源中心是企业付给供应商的能源账本，不是付给司机的油补，也不是财务总账。**

不新建顶层 backend module，作为 `client` 子域落地，与 `billing/` `finance/` 平级：

| 层 | 路径 |
|----|------|
| ORM / Schema / Service / API | `backend/app/modules/client/{models,schemas,services,api}/energy/` |
| Worker | `backend/app/modules/client/workers/energy_sync_worker.py`，入口 `app/workers/energy_sync_main.py` |
| 前端 | `frontend/client/src/views/energy/`，路由 `/energy/*` |
| 接口前缀 | `/api/client/energy/*` |
| 表 | `biz_energy_*`，`__table_tier__ = business`，**无 `tenant_id`**（分库隔离） |

## 二、解耦契约（三条硬边界）

实现时不允许破例。这是本模块相对外部参考方案最重要的取舍：能源中心自成账本，**单向只读**对外，不写任务成本、不写工资单。

1. **只写 `biz_energy_*`**。不 UPDATE `biz_task`，不写 `biz_driver_payroll`，不建 `biz_task_finance_doc`。
2. **读业务主数据只走** `services/energy/refs/master_data_resolver.py`。车辆、司机、运力、任务、运单的查询全收敛到这一个文件；其余 energy 代码禁止直接 import `models/capacity`、`models/task`。
3. **外部读能源数据只走** `services/energy/adapters/energy_query_adapter.py`。签名稳定，一期无调用方：

```python
EnergyQueryAdapter.get_vehicle_energy_cost(db, vehicle_ids, start, end) -> dict[int, Decimal]
EnergyQueryAdapter.get_driver_energy_cost(db, driver_ids, start, end) -> dict[int, Decimal]
EnergyQueryAdapter.get_task_energy_cost(db, task_ids) -> dict[int, Decimal]
EnergyQueryAdapter.get_waybill_energy_cost(db, waybill_ids) -> dict[int, Decimal]
```

取数优先读 `biz_energy_cost_allocation` 预聚合，缺失时回扫消费流水。

### 2.1 与财务 / 计费的口径

| 对象 | 本期做法 | 原因 |
|------|---------|------|
| 充值 | 充值单自带「登记付款」，记录银行账户与凭证 | 系统没有独立付款单表；接入出纳需改 `PayableDocKind` 与打款批次 |
| 能源成本进利润 | **不做** | 接入需改 `profit_accounting_service._cost_docs`；口径已定：充值类比预付不计成本，消费确认才计 |
| 司机垫付加油 | `source_channel=4` 且 `is_ledger_affecting=0` | 只进统一台账做分析，不扣能源账户、不参与成本归集，避免与任务费用单重复计成本 |
| `fuel_subsidy`（油补） | 不在本模块记账 | 油补是**付给司机的补贴**；能源消费是**付给供应商的能源费**，两笔钱不重复 |

代码里以 `# 二期接入点` 标出充值进出纳、成本进利润两处，不要提前改财务内核。

### 2.2 车辆能源属性放哪

`biz_vehicle` / `biz_vehicle_ext` 没有运输车辆自身的燃料类型和油箱容量（`biz_vehicle_series.energy_type` 是被运输商品车的属性）。补在 **`biz_energy_vehicle_profile`**，不改运力模块。

## 三、菜单与版本

一级菜单「能源中心」，`path=/energy`，`sort_order=450`（计费中心 400 与审批中心 500 之间）。菜单 id **1284–1324**（分配前已查 `sys_menu` 空档，含软删墓碑）。

总览页由前端 `injectModuleOverview` 自动注入，**不入库**。

```
能源中心 /energy
├── 能源账户     /energy/account      energy_account
├── 能源卡       /energy/card         energy_account
├── 充值管理     /energy/recharge     energy_account
├── 能源消费     /energy/consumption  energy_consumption
├── 数据接入     /energy/connector    energy_consumption
├── 能源对账     /energy/recon        energy_recon
├── 异常中心     /energy/exception    energy_risk
├── 成本分析     /energy/analysis     energy_analysis
├── 供应商与站点 /energy/supplier     energy_account
└── 能源设置     /energy/setting      energy_account（商品 / 车辆档案；风控阈值 API 走 energy_risk）
```

| feature_code | 名称 | 版本 | required_tables 要点 |
|--------------|------|------|----------------------|
| `energy_manage` | 一级容器 | standard / pro | 无表 |
| `energy_account` | 供应商 / 站点 / 商品 / 档案 / 账户 / 卡 / 充值 / 流水 | standard / pro | 主数据 + 账户介质 + 资金账本 |
| `energy_consumption` | 消费台账 / 数据接入 / 归集 | **仅 pro** | raw / consumption / connector / sync_task / allocation |
| `energy_recon` | 对账 | **仅 pro** | recon / recon_item |
| `energy_risk` | 风控异常 | **仅 pro** | rule / exception |
| `energy_analysis` | 成本分析 | **仅 pro** | snapshot / allocation（复用） |

API 路由在 `client/api/__init__.py` 用 `require_feature("energy_xxx")` 硬门控。租户管理员与超管见全量已开通 feature 的菜单；其余角色靠 `sys_role_menu`。

## 四、术语

| 术语 | 含义 |
|------|------|
| 能源账户 | 企业对某个供应商的预付 / 月结 / 授信账本，余额只能由流水改变 |
| 账面余额 `ledger_balance` | `Σ biz_energy_account_txn.delta`，唯一事实来源 |
| 可用余额 | `ledger_balance - frozen_amount`，**不落库** |
| 供应商侧余额 | 对方系统里看到的余额，用于对账，可空 |
| 能源卡 | 介质；绑定历史带时间区间，不能覆盖写 |
| 消费流水 | 标准化后的加油 / 加气 / 充电记录 |
| 原始层 raw | 供应商原样 JSON + `data_hash` 去重，只增不改 |
| 是否入账 `is_ledger_affecting` | 1 才扣能源账户并进成本归集 |
| 油补 | 计费成本政策里付给司机的补贴，与本模块无关 |

## 五、一期范围与二期锚点

### 5.1 一期已交付

- 主数据、账户、卡、充值、记账内核（含单元测试）
- Excel / 手工接入 + HTTP 连接器样板（真实三方 API 按样板补类，不动主链路）
- 消费标准化、匹配、归集、对账、风控、分析页
- 独立 worker（必须在 `deploy/docker/docker-compose.yml` 注册 `backend-energy-worker`，漏了线上永不跑）

### 5.2 一期明确不做

| 不做 | 原因 / 二期路径 |
|------|----------------|
| 中石油 / 中石化 / 万金油 / G7 真实对接 | 无对方文档与测试账号；插件框架已留 `@register_connector` |
| 充值进出纳打款批次 | 改 `PayableDocKind` + `_DOC_MODELS` |
| 能源成本进利润核算 | 改 `_cost_docs`；仅 `is_ledger_affecting=1` 的已确认消费 |
| GPS / 北斗里程作百公里分母 | `biz_task` 无 `distance_km`；一期用消费流水 `mileage` / `odometer` |
| 改 `biz_vehicle_ext` 加燃料字段 | 用 `biz_energy_vehicle_profile` |
| 能源商品改走 `biz_dict` | 字典存不下标准单位与供应商映射 |

### 5.3 里程与商品的已拍板决策

1. **百公里能耗分母**：消费流水上的 `mileage`（可手工录表显 `odometer`）。有 GPS 数据源后再换分母，分析服务不要去扫不存在的 `biz_task.distance_km`。
2. **能源商品建表** `biz_energy_product`，不进租户字典。
