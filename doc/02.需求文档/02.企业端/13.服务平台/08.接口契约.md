## 1. 通用约定

### 1.1 响应格式

沿用项目统一格式（`app/common/response.py`）：

```json
{ "code": 0, "message": "操作成功", "data": {} }
```

分页统一为 `{ "list": [], "total": 0, "page": 1, "pageSize": 20 }`。

### 1.2 命名

请求与响应字段统一 **camelCase**，与 `biz_task` 等既有模块一致（Schema 中直接写驼峰字段名，不用 `alias_generator`）。DB 列名是下划线，转换在 Schema 层完成。

### 1.3 路径前缀

| 端 | 前缀 |
|---|------|
| 租户端 | `/api/client/ecosystem` |
| 运营后台 | `/api/console/ecosystem` |

### 1.4 鉴权与门控

所有接口需要登录态。feature 门控通过依赖注入声明：

```python
@router.post("/posts/{post_id}/intents",
             dependencies=[Depends(require_feature("ecosystem_intent"))])
```

门控失败返回 `403`，`message` 由 `require_feature` 按 feature 映射为具体文案（见 §6.2），**不能返回「没有操作权限」这种通用话术**——用户需要知道是版本不够还是角色不够。

### 1.5 越权防线

按 `01` §6.2 的三条铁律，本模块所有 Repository 方法**必须显式接收 `viewerTenantCode`**，禁止从上下文隐式读取。Service 层不允许直接拼装可见性条件，一律调用 `EcoVisibilityFilter.apply()`。

## 2. 字段可见性矩阵

这是本模块最容易出错、也最不能出错的部分。四个层级的定义见 `04` §3.1。

### 2.1 层级判定

| 层级 | 判定条件 |
|------|---------|
| L1 匿名层 | 已登录，但所属租户未完成营业执照核验 |
| L2 认证层 | 所属租户 `license_verified = 1` |
| L3 洽谈层 | 与该挂牌之间存在 `status = 1`（洽谈中）或更后的意向 |
| L4 成交层 | 与该挂牌之间存在 `sys_eco_deal` 且 `status >= 1` |

层级是**针对「查看方 × 具体挂牌」这一组合**计算的，不是租户的全局属性。同一个查看方对 A 挂牌是 L3、对 B 挂牌可能只是 L2。

### 2.2 货源挂牌字段可见性

| 字段 | L1 匿名 | L2 认证 | L3 洽谈 | L4 成交 | 发布方本人 |
|------|:------:|:------:|:------:|:------:|:---------:|
| `postNo` `title` `postType` `status` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `fromProvince` `fromCity` `toProvince` `toCity` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `fromDistrict` `toDistrict` `fromName` `toName` | ✗ | ✓ | ✓ | ✓ | ✓ |
| `windowStart` `windowEnd` | 精确到日 | ✓ | ✓ | ✓ | ✓ |
| `totalQuantity` `quantityUnit` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `cargoCategory` `vehicleCondition` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `cargoItems`（品牌车系明细） | 仅品牌 | ✓ | ✓ | ✓ | ✓ |
| `priceType` `priceNegotiable` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `priceAmount` | 区间 | ✓ | ✓ | ✓ | ✓ |
| `requireTruckTypes` `requireSlotMin/Max` `allowSplit` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `otherRequirements` `settleType` `prepayRatio` | ✗ | ✓ | ✓ | ✓ | ✓ |
| `ownerMaskedName` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `ownerTenantName`（企业全称） | ✗ | 按挂牌 `visibilityLevel` | ✓ | ✓ | ✓ |

### 2.3 运力挂牌字段可见性

| 字段 | L1 匿名 | L2 认证 | L3 洽谈 | L4 成交 | 发布方本人 |
|------|:------:|:------:|:------:|:------:|:---------:|
| `truckType` `slotCount` `truckLength` `ratedLoad` `truckQuantity` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `plateMasked`（如 `浙A·**·88`） | ✗ | ✓ | ✓ | ✓ | ✓ |
| `plateNumber`（完整车牌） | ✗ | 仅当 `platePublic=1` | ✓ | ✓ | ✓ |
| `driverDisplay`（如「王师傅」） | ✗ | ✓ | ✓ | ✓ | ✓ |
| `driverYears` `driverOrderCount` | ✗ | ✓ | ✓ | ✓ | ✓ |
| `hasTrailer` `trailerPlateNumber` | ✗ | 打码 | ✓ | ✓ | ✓ |
| `goodAtCategories` `canInvoice` `hasInsurance` `servicePromise` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `departureReadyAt` `pickupRadius` | ✗ | ✓ | ✓ | ✓ | ✓ |
| `anyDirection` `destinations` | ✓ | ✓ | ✓ | ✓ | ✓ |

### 2.4 三条永不返回的字段

以下字段**在任何层级、任何接口、对任何人都不返回**，包括运营后台的常规列表页：

| 字段 | 原因 |
|------|------|
| `capacity_post.driver_name`（司机真实姓名） | 个人敏感信息。对外只给 `driverDisplay`；成交后由承运方在履约节点中主动提供 |
| 司机手机号 | 不落平台库（见 `07` §4.4）。成交后走 `sys_eco_deal.driver_phone`，且仅对成交双方可见 |
| 任何 VIN、客户名称、货主单位 | 绝对禁止进入平台库。这是 `01` §6.2 规则 3 的硬约束，发布时在 Service 层就要过滤掉 |

> 运营后台若因核查需要查看司机姓名，走独立的「敏感信息调阅」接口，单独鉴权并记 `sys_operation_log`。该接口一期不做，二期按需评估。

### 2.5 实现约定

可见性裁剪由**一处统一实现**完成：

```python
class EcoPostSerializer:
    """挂牌序列化器：唯一允许决定字段可见性的地方"""

    def serialize(self, post: SysEcoPost, viewer: EcoViewerContext) -> dict:
        level = self._resolve_level(post, viewer)   # L1~L4 或 OWNER
        ...
```

禁止在 Router 或 Service 里做 `if level >= 2: data["contactPhone"] = ...` 这类零散判断。**可见性逻辑分散一次，就等于埋下一个数据泄露入口。**

## 3. 租户端接口

### 3.1 大厅列表

```text
GET /api/client/ecosystem/halls/{hallType}/posts
```

`hallType` = `cargo` | `capacity`。

**Query 参数**

| 参数 | 类型 | 说明 |
|------|------|------|
| `page` `pageSize` | int | 默认 1 / 20 |
| `keyword` | string | 匹配标题、起讫地名 |
| `fromProvince` `fromCity` | string | 出发地 |
| `toProvinces` | string[] | 目的地省，多选；命中 `sys_eco_post_dest` 或 `anyDirection=1` |
| `windowStartFrom` `windowStartTo` | date | 时间窗范围 |
| `quantityMin` `quantityMax` | int | 数量范围 |
| `truckTypes` | string[] | 车型（运力大厅筛车型 / 货源大厅筛要求车型） |
| `slotMin` `slotMax` | int | 位数区间 |
| `cargoCategory` | int | 货类（货源大厅） |
| `priceType` | int | 计价方式 |
| `onlyVerified` | bool | 只看已认证企业，默认 `false` |
| `onlyHighCredit` | bool | 只看完成率 ≥ 90% 且评分 ≥ 4.5，默认 `false` |
| `excludeMine` | bool | 排除自己发布的，默认 `true` |
| `sortBy` | string | `latest`（默认）/ `windowStart` / `active` / `priceAsc` / `priceDesc` |

**响应** `data.list[]` 元素（按 §2 裁剪后的卡片视图）

```json

  "destinations": [{ "province": "四川省", "city": "成都市" }],
  "anyDirection": 0,
  "windowStart": "2026-07-27 08:00:00", "windowEnd": "2026-07-28 18:00:00",
  "totalQuantity": 8, "quantityUnit": "台", "remainingQuantity": 8,
  "priceType": 2, "priceAmount": 850.00, "priceIncludeTax": 0, "priceNegotiable": 1,
```

三个给前端省事的字段：

| 字段 | 作用 |
|------|------|

### 3.4 发布货源

```text
POST /api/client/ecosystem/cargo-posts/from-task    # 从任务单发布
POST /api/client/ecosystem/cargo-posts              # 手工发布
```

**从任务单发布的请求**

```json
{
  "taskId": 55012,
  "validDays": 7,
  "priceType": 2,
  "priceAmount": 850.00,
  "priceIncludeTax": 0,
  "priceNegotiable": 1,
  "settleType": 2,
  "allowSplit": 0,
  "requireTruckTypes": ["轿运车"],
  "requireSlotMin": 6,
  "otherRequirements": "需要能进厂区，车高不超过 4.2 米",
  "contactName": "李经理",
  "contactPhone": "13800138000",
  "visibilityLevel": 2,
  "contactVisibility": 3,
  "applyBlockRule": 1,
  "extraBlockTenants": ["nb002"],
  "titleOverride": null,
  "submitNow": true
}
```

后端从 `biz_task` 抽取线路、货物明细、装车时间、台数并生成标题，**不接受前端传这些字段**——前端能改的只有报价、要求、联系方式、可见性这几项用户真正需要决策的内容。这样做的代价是前端无法预览标题，因此提供一个 dry-run 接口：

```text
POST /api/client/ecosystem/cargo-posts/from-task/preview
```

同样的入参，返回将要生成的挂牌内容但不落库，供发布弹层第二步展示（见 `05` §5）。

**校验规则**（失败文案见 §6.1）

| 顺序 | 校验 |
|:---:|------|
| 1 | 任务单存在且属于当前租户 |
| 2 | 任务状态在允许发布的集合内（已配载 / 待调度） |
| 3 | 任务未指派承运方（`capacity_id` 与 `carrier_id` 均为空） |
| 4 | 该任务没有处于非终态的挂牌（查 `biz_eco_post_ref`） |
| 5 | 装车时间未过期 |
| 6 | 租户 `hall_enabled = 1` 且 `publish_restricted_until` 已过或为空 |
| 7 | 敏感内容硬拦截（联系方式、外部平台引流，见 `04` §2.3） |

**响应**

```json
{
  "id": 10231,
  "postNo": "HY202607250012",
  "status": 1,
  "auditStatus": 1,
  "estimatedAuditHours": 2,
  "whitelistPassed": false
}
```

`whitelistPassed = true` 时 `status` 直接是 `3`（展示中），前端提示文案随之不同。

| 顺序 | 校验 |

| 4 | 已绑定主驾司机且司机证件有效 |
| 5 | 该运力没有处于非终态的挂牌 |
| 6 | 时间窗合法（`windowStart` 不早于今天，`windowEnd` 晚于 `windowStart`） |
| 7 | `anyDirection = 0` 时 `destinations` 至少一项 |

### 3.6 挂牌管理

```text
GET    /api/client/ecosystem/my-posts                  # 我发布的
PUT    /api/client/ecosystem/cargo-posts/{id}
PUT    /api/client/ecosystem/capacity-posts/{id}
POST   /api/client/ecosystem/posts/{id}/submit          # 提交审核
POST   /api/client/ecosystem/posts/{id}/delist          # 停止展示
POST   /api/client/ecosystem/posts/{id}/relist          # 重新上架
POST   /api/client/ecosystem/posts/{id}/extend          # 延长展示天数
POST   /api/client/ecosystem/posts/{id}/refresh-source  # 从源单同步最新信息
```

`my-posts` 的 Query 支持 `postType`、`status`（多选）、`keyword`，并额外返回一个状态计数供 Tab 角标：

```json
{
  "list": [],
  "total": 42,
  "statusCounts": { "draft": 2, "auditing": 3, "listed": 12, "rejected": 1, "dealing": 5, "finished": 18, "delisted": 1, "cancelled": 0 }
}
```

`dealing` 合并「已锁定」与「履约中」——用户视角里它们是同一件事（这单已经谈成、正在往下走），分两个 Tab 只会让人不知道该点哪个。`statusCounts` 的所有键恒定返回，缺失的补 0，前端拿 `undefined` 会渲染成 `NaN`。

**`my-posts` 与大厅列表用的是两套不同的查询边界**，实现时不要互相套用：大厅按可见性收口（屏蔽名单、仅展示中、未过期），`my-posts` 按归属收口（`ownerTenantCode` 恒在条件里），且**不过滤状态与有效期**——草稿、被驳回、已过期的挂牌必须出现在列表里，否则用户没有入口去处理它们。已过期但状态仍为「展示中」的挂牌由前端按 `validUntil` 打「已过期」标签并突出「延长展示」。

编辑核心信息会使挂牌回到待审核状态并从大厅移出（分档规则见 `04` §2.4）。这个副作用必须由前端在提交前用二次确认说清楚（`05` §6.2），后端在响应里回传 `requireReaudit: true` 作为兜底提示，并回传 `changedLabels`（如 `["报价", "联系方式"]`）用于提示文案。**要向用户说明的是：重审期间已有的洽谈不受影响。**

`extend` 与 `relist` 的分工不能混：`extend` 只作用于「展示中」的挂牌、不改状态、不重审；已下架的（含到期下架）必须走 `relist`，重新审核并重算有效期。混在一起就等于给了一条「过期后延一天即可继续展示、永不复审」的路。`relist` 还会拦住装车时间已过的挂牌，要求先改时间。

### 3.7 合作意向

```text

POST   /api/client/ecosystem/intents/{id}/messages
```

**发起意向的请求**

一次 `select` 在同一事务内做五件事，任一失败全部回滚：

1. 该意向 → `已选定`
2. 生成 `sys_eco_deal`（`status = 0` 待确认，`confirm_deadline = now + 24h`）

5. 回写 `biz_eco_post_ref.deal_count`（失败进重试队列，不阻塞主事务）

## 4. 运营后台接口

### 4.1 审核

```text
GET    /api/console/ecosystem/posts/options               # 驳回原因、状态、类型等下拉元数据
GET    /api/console/ecosystem/posts                      # 全量检索
GET    /api/console/ecosystem/posts/pending              # 待审队列
GET    /api/console/ecosystem/posts/spot-check           # 抽检队列（免审直通已上架）
GET    /api/console/ecosystem/posts/backlog              # 积压统计（顶部数字卡）
GET    /api/console/ecosystem/posts/{id}                 # 审核详情
POST   /api/console/ecosystem/posts/{id}/approve
POST   /api/console/ecosystem/posts/{id}/reject
POST   /api/console/ecosystem/posts/batch-approve
POST   /api/console/ecosystem/posts/{id}/force-delist
POST   /api/console/ecosystem/posts/{id}/spot-check-pass
POST   /api/console/ecosystem/posts/{id}/spot-check-fail
POST   /api/console/ecosystem/posts/{id}/toggle-top      # 置顶（冷启动运营手段，二期）
```

`/options` 由后端下发驳回原因及其**模板文案**（`template`）与「是否必须补充说明」（`reasonRequired`）：运营在界面上选原因时就能看到「不写补充说明时租户会收到哪句话」，避免套用了一句不合适的模板而不自知。状态、审核状态、挂牌类型的中文名一并下发，运营后台不再各维护一份状态码字典。

`precheckFlags` 也在 `/options` 里下发（编码 → 中文名）。挂牌上落库的 `precheck_flags` 只有编码（`new_tenant`、`was_force_delisted` 等），预检当场那句人话并没有持久化，所以措辞必须由后端给：让前端自己配一份，同一个标记很快就会在队列和详情里显示成两个名字，而新增一条可疑规则时也没人记得去改前端。

`toggle-top` 一期不实现：置顶是冷启动期的人工运营手段，需要配套的置顶位数量与到期回收规则，与审核链路无关，留到运营看板一起做。

三个队列的排序口径不同，不能合并成一个接口靠参数区分：待审按 `submittedAt` 正序（等最久的先处理），抽检按 `listedAt` 正序（上架最久的最该复核），全量检索按 `submittedAt` 倒序（运营是来查最近发生了什么）。

**队列行**除挂牌本身外附带三个时效字段，前端直接用来标色和展示，不在前端重算：

```json
{
  "post": { },
  "waitedMinutes": 95,
  "urgency": 1,
  "urgencyLabel": "即将超时",
  "deadline": "2026-07-25 21:30:00"
}
```

`waitedMinutes` 是**工作时段分钟数**，不是自然时长（口径见 `04` §2.6）。前端展示成「已等待 1 小时 35 分」即可，不要自己拿 `submittedAt` 和当前时间相减，那样凌晨提交的会显示成 7 小时。

**积压统计**返回 `pending` / `pendingOverdue` / `pendingFlagged` / `spotCheckPending` / `spotCheckOverdue` 五个数，`pendingFlagged` 是命中可疑标记的待审数——它和超时数一起决定运营先看哪一堆。

**筛选参数**：`postType`、`tenantCode`、`keyword`（挂牌号 / 标题 / 租户名）、`flaggedOnly`、`overdueOnly`、`statuses`、`auditStatuses`、`submittedFrom` / `submittedTo`。三个接口共用同一套条件（运营在待审队列里筛好条件切到全量检索时，条件不该失效），其中 `statuses` / `auditStatuses` / `submittedFrom` / `submittedTo` 仅全量检索使用；抽检队列不接受 `overdueOnly`——抽检的时限口径是「上架后 `SPOT_CHECK_HOURS` 小时内复核」，与人工审核的工作时段 SLA 不是一回事，共用一个参数名会让两边都算错。

队列行另附 `isOverdue`，前端标红直接用它，不要拿 `waitedMinutes` 和阈值自己比。

**审核详情**要把审核员需要的所有判断依据一次给全，避免来回切页面：

```json
{
  "post": { },
  "sla": { "waitedMinutes": 95, "urgency": 1, "urgencyLabel": "即将超时", "deadline": "2026-07-25 21:30:00", "isOverdue": false },
  "precheck": {
    "flags": [
      { "code": "contact_in_text", "level": "block", "field": "otherRequirements", "hint": "「其他要求」里出现了手机号" },
      { "code": "price_abnormal", "level": "warn", "hint": "报价 850 元/台，低于该线路近 30 天均价 1200 元/台的 40%" }
    ],
    "flagCount": 2,
    "hasBlocking": true
  },
  "ownerContext": {
    "tenantCode": "hz001",
    "tenantName": "杭州佳达物流有限公司",
    "versionCode": "standard",
    "licenseVerified": 1,
    "publishCount": 23,
    "rejectCount": 1,
    "forceDelistCount": 0,
    "reportValidCount": 0,
    "rejectCountRecent": 0,
    "forceDelistCountRecent": 0,
    "spotCheckFailCount": 0,
    "dealCount": 6,
    "dealCompletedCount": 5,
    "firstPublishAt": "2026-05-12 09:20:00",
    "auditWhitelist": false,
    "whitelistRevokedAt": null,
    "whitelistRevokeReason": null,
    "recentPosts": [{ "postNo": "HY202607200008", "status": 6, "auditStatus": 2 }]
  },
  "sourceCheck": {
    "hasSource": true,
    "sourceType": 1,
    "sourceId": 5001,
    "snapshotAt": "2026-07-25 09:00:00",
    "sourceChanged": 0,
    "sourceChangedAt": null,
    "sourceConsistent": true,
    "hint": "由系统单据带出，内容与单据一致"
  },
  "whitelistEligibility": { },
  "auditTrail": [
    { "action": 3, "actionLabel": "审核驳回", "reasonLabel": "联系方式违规", "reason": "…", "operatorName": "李运营", "createdAt": "2026-07-24 15:02:11" },
    { "action": 14, "actionLabel": "编辑挂牌", "changedFields": { "totalQuantity": { "old": 8, "new": 12 } }, "operatorName": "张三", "createdAt": "2026-07-25 08:50:03" }
  ]
}
```

`sourceCheck.sourceConsistent` 是审核员最需要的一条信息：**这条挂牌背后是否真有一张任务单，且内容对得上。** 有源单且一致的挂牌，虚假信息的概率极低，可以快速通过。判据是 `source_changed` 标记（源单变更钩子写入）；**手工发布的挂牌返回 `null` 而不是 `true`**——没有源单可比就是「无从核验」，把它说成「一致」会让审核员对最该警惕的一类挂牌放松要求。`hint` 是可直接展示的成句文案。

`sla` 与队列行同口径（同一个算法，见 `04` §2.6），详情页顶部直接展示，不要在详情页里另算一遍等待时长——两处对不上时审核员不知道该信哪个数。

`auditTrail` 给最近 20 条流转记录。带上它是因为「上一轮为什么被驳回、租户之后改了哪些字段」决定了这一轮该重点看什么；不给流水，同一个问题会被反复发现。编辑动作附 `changedFields`（新旧值对照）。

`whitelistEligibility` 与 §4.2 的资格判定同结构。审核详情里已经聚合过发布方档案，顺手复用它算出资格，运营在通过一条挂牌时就能顺手把符合条件的企业放进免审白名单，不用再切页面。

`ownerContext` 里带 `Recent` 后缀的三个计数是 90 天回溯窗口内的数（`WHITELIST_CLEAN_DAYS`），与不带后缀的累计数并列给出：一个租户去年被强制下架过一次、今年干干净净，和上周刚被下架过，是两种完全不同的情况，只给累计数会让审核员对老用户过度警惕。这些数字**实时聚合**，不读 `sys_eco_tenant_credit` 的冗余计数——信誉统计是给展示用的、允许有延迟，审核判断不能建立在可能过期的数上。

**驳回**

```json
{ "reasonCode": 3, "reason": "「其他要求」里写了手机号，请删掉后重新提交，联系方式会在双方达成洽谈后自动互通" }
```

`reasonCode` 必填（枚举见 `04` §2.5），`reason` 选填但选「其他」时必填。`reason` 会**原样展示给租户**，因此必须写成人话并给出可行动的下一步；不填时后端按 `reasonCode` 套内置模板，绝不会把「信息不真实」四个字直接甩给租户。

**批量通过**返回逐条结果，不是一个成功数：

```json
{
  "successCount": 47,
  "succeeded": ["HY202607250001", "…"],
  "failed": [
    { "postId": 812, "postNo": "HY202607250019", "message": "这条挂牌已经被发布方撤回了，不用再处理" }
  ],
  "message": "已通过 47 条，另外 3 条没能处理，请看下面的原因"
}
```

单次上限 50 条，超出直接拒绝并提示分批。**部分失败仍返回成功响应**，前端按 `failed` 是否为空决定用成功提示还是带明细的警告弹层——把它当整体失败处理会让运营以为 47 条也没生效，重复点击。

**强制下架**的 `revokeWhitelist` 默认 `true`（下架一条却留着免审，下一条照样直通上架）。挂牌已进入成交时接口返回业务失败，文案直接给出「请到成交单里走终止流程」的指引。

### 4.2 白名单与租户管控

```text
GET    /api/console/ecosystem/audit-whitelist                            # 成员列表
GET    /api/console/ecosystem/audit-whitelist/{tenantCode}/eligibility   # 资格判定 + 租户档案
POST   /api/console/ecosystem/audit-whitelist                            # 授予
POST   /api/console/ecosystem/audit-whitelist/{tenantCode}/revoke        # 移出，必填原因
POST   /api/console/ecosystem/tenants/{tenantCode}/verify        # 认证核验打标（二期）
POST   /api/console/ecosystem/tenants/{tenantCode}/toggle-hall   # 开关大厅能力（二期）
POST   /api/console/ecosystem/tenants/{tenantCode}/restrict      # 限制发布/意向权限（二期）
GET    /api/console/ecosystem/tenants/{tenantCode}/credit        # 已并入 eligibility 返回
```

移出用 POST 而不是 DELETE：原因是必填业务参数（写入 `whitelist_revoke_reason`，并作为冷静期起点），而 DELETE 带请求体在网关、日志采集、前端请求库这几层都属于少见路径，最典型的故障是「体被丢掉、后端收到空原因」。

**成员列表**每行带发布量、成交量与违规数，运营扫一眼就能发现「这家已经被强制下架过 2 次却还在白名单里」这类漏处置。

**资格判定**返回逐条明细而不是一个布尔值，界面上直接告诉运营还差什么。租户档案（§4.1 的 `ownerContext` 同结构）一并返回，白名单页与审核详情页因此可以共用同一个组件：

```json
{
  "tenant": { "tenantCode": "hz001", "publishCount": 23, "…": "同 ownerContext" },
  "eligibility": {
    "tenantCode": "hz001",
    "eligible": false,
    "manualAllowed": true,
    "summary": "累计发布 3 条，还差 2 条；2026-07-13 被移出过，2026-08-12 之后才能重新进入",
    "items": [
      { "code": "license_verified", "label": "企业认证", "passed": true, "detail": "已通过营业执照核验", "blocking": true },
      { "code": "publish_volume", "label": "历史挂牌", "passed": false, "detail": "累计发布 3 条，还差 2 条", "blocking": false },
      { "code": "recover_period", "label": "冷静期", "passed": false, "detail": "2026-07-13 被移出过，2026-08-12 之后才能重新进入", "blocking": false }
    ]
  }
}
```

七个 `code`：`hall_enabled`、`license_verified`、`publish_volume`、`no_reject`、`deal_record`、`no_violation`、`recover_period`。`blocking: true` 的项**人工也不能豁免**（仅前两个，理由见 `04` §2.2）。`eligible` 是自动准入结论，`manualAllowed` 是人工能否强行授予——两者分开返回，界面才能在「不满足自动条件但运营可以拍」时把按钮留着；一律灰掉只会逼运营去改数据库。

`detail` 是可直接展示的成句文案，前端不要自己按 `passed` 拼「未满足」之类的话，那样运营看不到差多少。

**移出白名单必须带原因**，写入 `whitelist_revoke_reason` 并记 `whitelist_revoked_at`：前者给下一个运营看（免得重复排查同一件事），后者用于阻止自动任务在冷静期内把它加回来。授予与移出都走 `sys_operation_log`。

`summary` 是把所有未满足项拼成的一句话，用于「授予被拒」时的错误提示——错误提示只能说一句话，而这里要表达七个条件的差距。

### 4.3 举报与看板

```text
GET    /api/console/ecosystem/reports
POST   /api/console/ecosystem/reports/{id}/handle
GET    /api/console/ecosystem/dashboard                  # 生态看板
```

看板指标：挂牌数（按状态/类型）、意向发起率、意向响应率、平均响应时长、成交数与金额、审核时长 P50/P90、待审积压数、举报数与成立率、活跃租户数。

## 5. 幂等与并发

| 场景 | 风险 | 处理 |
|------|------|------|
| 重复发布同一任务单 | 产生两条相同挂牌 | 校验 4（查 `biz_eco_post_ref`）+ Redis 短锁 `eco:publish:{tenantCode}:{sourceType}:{sourceId}`，TTL 10 秒 |
| 两个用户同时选定不同意向 | 一个挂牌出两个成交单 | `select` 时对挂牌行加 `SELECT ... FOR UPDATE`，再校验 `status = 3` |
| 同时发起重复意向 | 同一租户对同一挂牌两条意向 | Redis 锁 `eco:intent:{postId}:{tenantCode}` + 事务内复查 |
| 批量通过审核 | 部分成功部分失败 | 逐条独立事务，返回 `successCount` / `failedItems`，不用大事务 |
| 履约节点重复上报 | 时间线出现重复项 | 允许重复（同节点可多次更新位置），前端按 `milestoneType` 分组取最新 |

## 6. 错误文案

按 `.cursor/rules/humanized-ux-copy.mdc`，`BizException` 的文案**直接展示给用户**，必须说清发生了什么以及下一步做什么，不能出现字段名、状态码、表名。

### 6.1 业务校验

| 场景 | 文案 |
|------|------|
| 任务单不存在或不属于本租户 | 没有找到这个任务，请刷新页面后重试 |
| 任务状态不允许发布 | 只有已配载、还没安排车的任务才能发布到货源大厅 |
| 任务已指派承运方 | 这个任务已经安排了承运方，不需要再发布到大厅 |
| 任务已有挂牌 | 这个任务已经在货源大厅展示了，可以到「我发布的」里查看 |
| 装车时间已过 | 装车时间已经过了，请先调整任务的装车时间 |
| 运力不空闲 | 这台车正在运输中，暂时不能发布 |
| 运力证照过期 | 这台车的道路运输证已过期，请先在运力档案里更新证照 |
| 运力未绑定司机 | 这台车还没有绑定主驾司机，请先完善运力档案 |
| 运力已有挂牌 | 这台车已经在运力大厅展示了，可以到「我发布的」里查看 |
| 未填目的地 | 请选择希望前往的方向，或者勾选「任意方向都可以」 |
| 时间窗不合法 | 可用结束时间要晚于开始时间 |
| 挂牌不在展示中 | 这条信息刚刚被下架了，看看大厅里其他的吧 |
| 挂牌已被锁定 | 这条信息已经有人接了，看看大厅里其他的吧 |
| 挂牌已过期 | 这条信息已经过期了，看看大厅里其他的吧 |
| 对自己的挂牌发起意向 | 这是你自己发布的信息 |
| 重复发起意向 | 你已经联系过这一条了，可以到「我的合作」里继续沟通 |
| 意向已被婉拒/撤回 | 这条洽谈已经结束了 |
| 挂牌方已选定他人 | 对方已经选择了其他合作方，看看大厅里其他的吧 |
| 确认超时 | 确认时间已经过了，这笔合作已自动取消 |
| 已评价过 | 你已经评价过这次合作了 |
| 评价窗口关闭 | 合作完成超过 15 天后就不能再评价了 |
| 内容含联系方式 | 为了保障双方安全，信息里不能填手机号或微信号。达成洽谈后系统会自动互通联系方式 |
| 内容含外部引流 | 信息里不能出现其他平台的名称或链接 |
| 大厅能力被关闭 | 你的账号暂时不能使用货源大厅，具体情况请联系客服 |
| 发布权限被限制 | 因为之前有信息被核实不实，发布功能暂停到 8 月 1 日 |

### 6.2 权限与门控

| 场景 | HTTP | 文案 |
|------|:---:|------|
| 无 `ecosystem_intent`（standard 等） | 403 | 主动联系同行是专业版的能力。你现在已经可以发布自己的货源和运力，升级后还能主动出击 |
| 无 `ecosystem_*_publish`（lite 等） | 403 | 发布信息需要标准版及以上，升级后就能把吃不下的货和跑不满的车交给同行了 |
| 未完成企业认证 | 403 | 完成企业认证后就可以联系对方了，认证一般当天就能通过 |
| 缺少菜单按钮权限 | 403 | 你的账号没有这个操作权限，可以让管理员在「角色管理」里开启 |
| 越权访问他人挂牌管理接口 | 403 | 没有找到这条信息，请刷新页面后重试 |

> 最后一条刻意用「没有找到」而不是「无权访问」。越权探测者不该从错误文案里确认目标资源的存在性，这是 `01` §6.2 之外的一层信息防护。

## 7. 前端 API 层组织

```text
frontend/client/src/api/ecosystem/
├── hall.ts          # 大厅列表、详情、筛选项、浏览上报
├── post.ts          # 发布、编辑、提交、下架、延期、源单同步
├── intent.ts        # 意向发起、响应、婉拒、撤回、留言、选定
├── deal.ts          # 成交、履约节点、完成、终止、评价、加承运商
├── profile.ts       # 企业名片、屏蔽名单、对方名片
├── subscription.ts  # 订阅（1.4）
├── report.ts        # 举报（1.4）
└── types.ts         # 全部 TS 类型定义
```

`types.ts` 的类型定义必须与本文严格一致。**约定：本文修改后，同一个 PR 内必须同步 `types.ts`**，否则前后端字段会静默漂移——这是跨端协作最常见也最难排查的一类问题。

状态与枚举的中文映射统一放 `frontend/client/src/config/ecosystem/enums.ts`，不在各页面各写一份 `statusMap`。
