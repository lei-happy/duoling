## 1. 分库原则

| 数据 | 库 | 理由 |
|------|----|----|
| 挂牌、目的地、审核流水、浏览记录、意向、留言、成交、履约节点、评价、企业名片、信誉、屏蔽名单、订阅、举报 | **平台库 `zt_platform`** | 全部是跨租户可见数据，必须集中；分散到租户库则大厅列表无法分页排序（见 `01` §2.2） |
| 发布关联关系 | **租户库 `zt_biz_{code}`** | 只服务本租户内部页面的角标与联动判断，跟着租户物理隔离 |

命名规范：平台库沿用 `sys_` 前缀，本模块统一二级前缀 `sys_eco_`（ecosystem）；租户库沿用 `biz_` 前缀。所有表继承基类的四个标准列 `id / created_at / updated_at / is_deleted`，下文字段表中不再重复列出。

## 3. 核心结构决策

### 3.1 共有筛选维度提到主表

`01` §3.2 原本的设想是「主表放内核字段、扩展表放业务字段」。落到索引层面时发现一个问题：**大厅列表的筛选条件（线路、时间、数量、价格）在扩展表，而状态与有效期在主表**，每次列表查询都要跨表组合条件，两张表的索引都用不满。

重新审视后发现，货源与运力在这几个维度上其实是**同构**的：

| 维度 | 货源含义 | 运力含义 |
|------|---------|---------|
| 出发地 | 起点 | 车当前所在地 |
| 目的地 | 终点 | 期望流向 |
| 时间窗 | 期望装车时间起止 | 可用时间起止 |
| 数量 | 总台数 | 可载台数 |
| 价格 | 期望运价 | 报价 |

既然同构，就应该放在主表由内核统一管理：**大厅列表查询变成主表单表扫描（目的地筛选走一次子查询），扩展表只在详情页 join 一次。** 扩展表退化为纯粹的「各自特有字段」容器。

这个调整让 §6 的列表 SQL 能完整命中一条联合索引，是本文相对 `01` 最重要的一处细化。

### 3.2 目的地单独成表

运力挂牌的期望流向是**多值**的（「我想往华东或华中走」），而目的地是核心筛选维度。三种实现的对比：

| 方案 | 问题 |
|------|------|
| 主表存 JSON 数组 + `JSON_CONTAINS` | 无法有效使用索引；MySQL 8.0.17+ 的多值索引可用但对版本有硬要求，风险不必要 |
| 主表存逗号分隔字符串 + `LIKE` | 全表扫描，且「四川」会匹配到「四川省」之外的脏数据 |
| **独立子表 + `EXISTS`** | ✓ 采用 |

`sys_eco_post_dest` 对**货源也写入一行**（终点），这样筛选逻辑对两个大厅完全统一，Service 层不需要 `if post_type` 分支——这与 `01` §4.1「内核代码里不允许出现 `if post_type == 1`」的约定一致。

「接受任意流向」的运力挂牌不写 dest 行，靠主表 `any_direction=1` 标记，筛选时用 `OR any_direction = 1` 兜住。

### 3.3 冗余归属租户编码

`sys_eco_intent`、`sys_eco_deal`、`sys_eco_post_view` 都冗余了挂牌的 `owner_tenant_code`。理由：这三张表都需要支持「按租户查自己相关的全部记录」，冗余一列可以避免每次都 join 主表，且让 `01` §6 的越权校验能在单表内完成——**越权防线越简单越可靠，值得付出一列冗余的代价。**

### 3.4 地区存代码而不是自增 ID

平台库的地区字段一律叫 `*_region_code`，存**行政区划代码**（如 `330100`），不存自增主键。

租户库里全项目的惯例是 `*_region_id` 指向 `biz_region.id`，但 `biz_region` 是各租户注册时**各自同步一份**的，同一个「杭州市」在不同租户库里 id 不同。把它写进平台库等于存了一个跨租户无意义的数字，而且看着像外键，后来的人一定会拿它去 join——**这是个会静默出错、不会报错的坑，所以字段名必须说实话。**

行政区划代码则天然全局稳定，且正好是平台 `sys_regions` 的主键（该表没有 `id` 列）。发布时由 `region_resolver` 把租户侧的 `region_id` 翻译成代码与省/市/区名。

### 3.5 进入审核队列的时间单独存一列

`sys_eco_post.submitted_at` 记录「这条挂牌是什么时候进审核队列的」，待审队列的排序与 SLA 计算都以它为基准，而不是 `created_at`。

不能沿用 `created_at` 的原因有两个：草稿可能躺三天再提交，编辑核心信息触发的完整重审更是发生在挂牌创建很久之后。用 `created_at` 排队列，老草稿会插到队首，刚回来重审的挂牌看起来已经等了三天——`04` §2.6 的「平均审核时长」「2 小时内处理率」「超时未处理数」三个指标会全部算错，而且是**算错了也不会有人发现**的那种错。

写入时机：首次发布、提交审核、重新上架、编辑触发完整重审，四处都重置为当前时间。免审直通同样写，它进的是抽检队列，一样要算等了多久。索引随之从 `(audit_status, created_at)` 换成 `(audit_status, submitted_at)`。

### 3.6 业务编号规则

| 表 | 字段 | 规则 | 示例 |
|----|------|------|------|
| `sys_eco_post` | `post_no` | `HY`/`YL` + `yyyyMMdd` + 4 位日流水 | `HY202607250001` |
| `sys_eco_intent` | `intent_no` | `YX` + `yyyyMMdd` + 4 位日流水 | `YX202607250012` |
| `sys_eco_deal` | `deal_no` | `CJ` + `yyyyMMdd` + 4 位日流水 | `CJ202607250003` |
| `sys_eco_report` | `report_no` | `JB` + `yyyyMMdd` + 4 位日流水 | `JB202607250001` |

编号在平台库生成，日流水用 Redis 自增键（`eco:seq:{prefix}:{yyyyMMdd}`，TTL 48 小时）保证并发唯一，DB 层的唯一索引作为最后防线。

Redis 丢键重启后 `INCR` 会从 1 重新开始，与当日已有编号全线撞车，因此**流水为 1 时必须回库核对当日最大值**；唯一索引冲突后的重试要用 `prefer_db=True` 直接以库内水位取号，否则会反复撞同一批号。实现见 `EcoNumberService`。

> 存 `eval_score_sum` 而不只存 `avg_score`，是为了让新增一条评价时可以用 `eval_score_sum = eval_score_sum + ?, eval_count = eval_count + 1` 原子递增，再算平均；否则每次新增评价都要重新聚合全表。

## 6. 关键查询模式

### 6.1 大厅列表（最高频）

以货源大厅「杭州出发 → 四川方向、7 天内装车、只看已认证」为例：

```sql
SELECT p.*
FROM sys_eco_post p
WHERE p.is_deleted = 0
  AND p.post_type = 1
  AND p.status = 3
  AND p.valid_until > NOW()
  AND p.from_province = '浙江省'
  AND p.from_city = '杭州市'
  AND p.window_start BETWEEN NOW() AND DATE_ADD(NOW(), INTERVAL 7 DAY)
  -- 目的地：走子表 EXISTS，兼容运力的多流向与任意流向
  AND (
    p.any_direction = 1
    OR EXISTS (
      SELECT 1 FROM sys_eco_post_dest d
      WHERE d.post_id = p.id AND d.is_deleted = 0
        AND d.province = '四川省'
    )
  )
  -- 屏蔽名单：对方屏蔽了我，我就看不到（注意索引方向）
  AND NOT EXISTS (
    SELECT 1 FROM sys_eco_block_rule b
    WHERE b.is_deleted = 0
      AND b.blocked_tenant_code = :viewer_tenant_code
      AND b.tenant_code = p.owner_tenant_code
  )
  -- 本条挂牌的额外屏蔽
  AND (
    p.extra_block_tenants IS NULL
    OR NOT JSON_CONTAINS(p.extra_block_tenants, JSON_QUOTE(:viewer_tenant_code))
  )
  -- 只看已认证
  AND EXISTS (
    SELECT 1 FROM sys_eco_tenant_profile tp
    WHERE tp.tenant_code = p.owner_tenant_code
      AND tp.license_verified = 1 AND tp.hall_enabled = 1
  )
  -- 不展示自己发布的（「找货」Tab 下）
  AND p.owner_tenant_code <> :viewer_tenant_code
ORDER BY p.is_top DESC, p.listed_at DESC
LIMIT 20 OFFSET 0;
```

驱动索引：`idx_eco_post_hall_from (post_type, status, from_province, from_city, window_start)`。

三个必须注意的点：

1. **这段 SQL 绝不允许在 Service 层手写。** 从 `is_deleted` 到「只看已认证」这一整套条件，任何一处漏掉都是数据泄露或信息污染，因此必须收敛到 `EcoVisibilityFilter.apply()` 中统一拼装（见 `01` §6.2 规则 1）。
2. **屏蔽名单的子查询方向容易写反。** 语义是「挂牌归属方把我加进了屏蔽名单」，所以条件是 `b.blocked_tenant_code = 查看方` 且 `b.tenant_code = 挂牌方`。写反了会变成「我屏蔽了谁就看不到谁」，虽然表面上也能跑通、结果集也非空，但完全违背设计意图且不会报错——是典型的静默 bug。
3. **`extra_block_tenants` 用 `JSON_CONTAINS` 无法走索引**，但它只在少数挂牌上非空，且已被前面的条件大幅缩小结果集，实际影响可忽略。若未来发现慢查询，再把它规范化成子表。

### 6.2 挂牌详情热度（发布方视角）

```sql
SELECT COUNT(DISTINCT viewer_tenant_code) AS viewer_count,
       viewer_province, COUNT(DISTINCT viewer_tenant_code) AS cnt
FROM sys_eco_post_view
WHERE post_id = :post_id AND is_deleted = 0
  AND view_date >= DATE_SUB(CURDATE(), INTERVAL 7 DAY)
GROUP BY viewer_province
ORDER BY cnt DESC;
```

走 `idx_eco_view_post (post_id, view_date)`。

### 6.3 我的合作（意向 + 成交）

意向要同时查「我发出的」和「我收到的」，分别走 `idx_eco_intent_initiator` 与 `idx_eco_intent_owner`，两个方向各自分页，**不要用 `OR` 合并成一条 SQL**——`OR` 会导致两个索引都用不上。前端本来也是分 Tab 展示的，正好对应两次查询。

### 6.4 待审队列

SELECT * FROM sys_eco_post
WHERE is_deleted = 0 AND audit_status = 1

## 8. 迁移方案

### 8.1 两条路径

| 表 | 库 | 机制 | 命令 |
|---|----|------|------|
| `sys_eco_*`（16 张） | 平台库 | Alembic versioned migration | `python -m scripts.migration.autogen platform --name "服务平台挂牌与撮合表"` |
| `biz_eco_post_ref`（1 张） | 租户库 | 新增表由 runner 按 `required_tables` 自动建，**不需要 versioned migration** | `python -m scripts.migration.autogen tenant --name "服务平台发布关联表"`（仅刷新 snapshot） |

按 `.cursor/rules/database-migration.mdc` 的强制要求，同一个 PR 内必须提交：ORM 文件 + migration 文件 + `snapshots/*.json`。提交前跑 `python -m scripts.migration.check` 确认无 drift。

### 8.2 分期建表

虽然分 1.1~1.4 四期开发，**建议 16 张平台库表一次性建完**，只是后期的表先不写入。理由：平台库 migration 是全局的，拆成四次会产生四个 revision，中间任何一次失败都要处理版本链；而空表的成本几乎为零。

### 8.3 存量租户

`biz_eco_post_ref` 对已有租户不会自动出现，需要一次性脚本（放 `backend/scripts/init/`）遍历所有 `db_initialized = 1` 的租户执行 `ensure_tenant_tables(["biz_eco_post_ref"])`。因为发布权开放到了 standard，覆盖范围是全部 standard 与 pro 租户；建议直接对所有已初始化租户执行。

### 8.4 初始化数据

| 数据 | 时机 | 说明 |
|------|------|------|
| `sys_eco_tenant_profile` | 懒加载 | 租户首次访问大厅时按 `sys_tenant` 自动创建一条，不预生成 |
| `sys_eco_tenant_credit` | 懒加载 | 同上 |
| 车辆类型字典 | 建表后 | 复用现有 `sys_dict`，新增字典 `eco_truck_type`、`eco_cargo_category`、`eco_eval_tag`、`eco_decline_reason` |

> 名片与信誉表用懒加载而非全量预生成：平台上多数租户短期内不会碰服务平台，预生成几千条空记录没有意义，还会让「有多少租户真的在用」这个运营指标失真。

## 9. 容量与清理

| 表 | 增长特征 | 策略 |
|---|---------|------|
| `sys_eco_post_view` | 增长最快（预估 200 万/年） | 保留 6 个月明细；超期按「挂牌 + 月」聚合后删除明细。清理任务挂到巡检 Worker |
| `sys_eco_post_audit` | 稳定增长 | 长期保留（审计需要），一年后可归档到冷表 |
| `sys_eco_intent_message` | 中速增长 | 长期保留，成交纠纷的凭证 |
| `sys_eco_post` | 挂牌进入终态后不再变化 | 不删除；终态挂牌超过 1 年可归档 |
| 其余表 | 量小 | 无需清理 |

平台库整体新增数据量在可控范围内（一年百万级），与现有平台库共用连接池即可，暂不需要读写分离或分库分表。
