## 1. 分期与里程碑

| 期次 | 目标 | 交付内容 | 可独立验收 |
|------|------|---------|-----------|
| **1.1 挂牌闭环** | 发得出去、审得过来、看得到 | 平台库表 + 撮合内核 + 货源/运力发布（任务单/运力档案/手工三来源）+ 运营审核 + 大厅浏览筛选 + 下架过期 + 源单联动 + 巡检 Worker + 企业名片与认证 | ✓ |
| **1.2 撮合闭环** | 联系得上、谈得成 | 合作意向发起/响应/婉拒/撤回 + 联系方式分层解锁 + 洽谈留言 + 选定与成交确认 + 挂牌锁定 + 通知 | ✓ |
| **1.3 履约闭环** | 跟得到、评得了、留得住 | 履约节点上报 + 完成确认 + 双方互评 + 信誉统计与展示 + 一键加为承运商 + 与任务单的回填引导 | ✓ |
| **1.4 运营增强** | 转得起来 | 订阅提醒 + 生态运营看板 + 免审白名单 + 举报处置 + 爽约处置 | ✓ |
| **2.x** | 跨租户直连 | 运单直通、服务大厅、智能推荐、在线结算 | 二期立项 |

**上线策略**：1.1~1.4 全部完成后**一次性灰度上线**，不分批放给用户。

> 理由：只做到 1.1 的产品是「能看不能联系」，用户来一次就不会再来，而且会形成「这功能没用」的第一印象，后续再补功能也很难挽回。分期的价值在于开发过程可验收、风险可控，不等于分批交付给用户。

### 2.3 数据库变更机制

两类表走两条不同路径，不要混：

| 表 | 库 | 机制 | 命令 |
|---|----|------|------|
| `sys_eco_*`（16 张） | 平台库 | Alembic versioned migration | `python -m scripts.migration.autogen platform --name "服务平台挂牌与撮合表"` |
| `biz_eco_post_ref`（1 张） | 租户库 | **新增表无需 versioned migration**，由 runner 按 `required_tables` 自动建 | 只需 `autogen tenant` 刷新 snapshot + 在 feature 的 `required_tables` 中登记 |

改完模型后必须按 `.cursor/rules/database-migration.mdc` 的要求执行：

```bash
cd backend
python -m scripts.migration.check                                  # 看 drift
python -m scripts.migration.autogen platform --name "服务平台挂牌与撮合表"
python -m scripts.migration.autogen tenant --name "服务平台发布关联表"
```

同一个 PR 内必须同时提交：模型文件 + migration 文件 + `snapshots/*.json`。

### 4.3 存量租户的建表

`biz_eco_post_ref` 是新表，已开通对应版本的存量租户不会自动拥有。需要一次性脚本遍历所有 `db_initialized=1` 的租户执行 `ensure_tenant_tables(["biz_eco_post_ref"])`，放在 `backend/scripts/init/` 下。

> 因为发布权开放到了 `standard`，这个脚本的覆盖范围是**全部 standard 与 pro 存量租户**，不是只有 pro。建议直接对所有 `db_initialized=1` 的租户执行——多建一张空表的成本远低于漏建导致的运行时报错。

## 5. 灰度与上线

| 阶段 | 做法 | 周期 |
|------|------|------|
| **内测** | 用 2~3 个内部测试租户跑通全流程，运营同学实际操作审核后台 | 1 周 |
| **定向邀请** | 挑 10~20 家有互补性的真实客户（有的车多、有的货多，线路能对上）单独开 `ecosystem_*_publish` 与 `ecosystem_intent`；运营主动电话邀约并陪跑首次发布 | 2~4 周 |
| **观察指标** | 挂牌数、意向发起率、意向响应率、成交数、审核时长、投诉数 | 同上 |
| **全量** | 指标达标后把 publish 类正式绑定到 `standard` + `pro`，`ecosystem_intent` 绑定到 `pro` | — |

**灰度实现**：不需要额外的灰度框架。给试点租户在 `sys_tenant_product` 上单独授权即可——这正是 feature 机制的设计用途。全量时按 §4.1 的映射写进 `VERSION_FEATURES`。

> 灰度期有一个必须注意的点：试点租户里**要同时包含 standard 和 pro**，且给部分 standard 租户临时开 `ecosystem_intent`、部分不开。只有这样才能在真实环境里验证「standard 只能被动等」这个体验到底能不能接受——这是本次商业设计里唯一没有先例可循、必须靠数据验证的假设。如果观察到 standard 挂牌的问询率长期低于 20%，就要重新考虑是否给 standard 每月赠送几次意向发起额度。

**冷启动准备**（这一步不能省）：

1. 定向邀请前，运营要先和客户访谈，确认真实意愿，不要上线了才发现没人愿意发
2. 大厅上线首日必须有内容。运营可以代已同意的客户录入种子挂牌（挂牌上标注「平台代发」，不伪装成客户自发）
3. 优先撮合几单**由运营人工牵线**的成交，用真实案例做后续推广素材

## 7. 测试要点

| 类别 | 要点 |
|------|------|
| **越权**（最高优先级） | A 租户读取/修改/下架 B 租户的挂牌、意向、成交、留言，全部必须被拒；构造 URL 直接改 ID 的场景 |
| **可见性** | 四个层级下返回字段的差异；确认 L1 层响应体中**不包含**联系方式字段本身，而非返回空值 |
| **屏蔽名单** | 被屏蔽方在列表、搜索、详情、订阅中都查不到；被屏蔽方无任何感知 |
| **feature 门控** | ① standard 能浏览、能发布、能处理收到的意向并完整成交，**不能主动发起意向**；② lite/ylb 能浏览、能处理收到的意向，不能发布；③ pro 全部可用；④ 全部判断走 `hasFeature`，不出现硬编码版本号 |
| **源单联动** | 逐条验证 `01` §5.3 与 `03` §6 的联动规则表；模拟同步失败后巡检 Worker 能修复 |
| **状态机** | 三条状态机的全部合法流转与非法流转；已锁定回退、超时作废、分批成交台数扣减 |
| **并发** | 两个租户同时对同一挂牌发起意向并被同时选定；分批承运的剩余台数并发扣减不超卖 |
| **审核** | 硬拦截规则逐条验证；免审白名单进出；快速复审与完整重审的区分 |
| **通知** | 三类短信事件触发准确，不重复发送 |
| **文案** | 全量走查是否符合《人性化交互提示语》，不出现技术黑话 |

测试用例文档新增：`doc/06.测试用例体系/02.企业端/15.服务平台.md`。

## 8. 风险与应对（实施角度）

> 产品层面的风险见 `00` §8，此处只列实施风险。

| 风险 | 影响 | 应对 |
|------|------|------|
| 钩子接入点遗漏，导致挂牌与源单脱节 | 信息污染 | 巡检 Worker 作为兜底必须在 1.1 就上线，不能延后；上线后前两周把巡检修正的数量作为监控指标，数量高说明钩子有遗漏 |
| 平台库集中存储引发越权 | 严重数据事故 | Repository 强制第一参数为 `viewer_tenant_code`；Code Review 时把「是否走了统一过滤器」列为必查项；越权单测必须在 CI 中运行 |
| 撮合内核抽象过度，两个大厅需求打架 | 开发返工 | 内核只负责生命周期与关系，任何「货源特有」「运力特有」的逻辑一律下沉到 Adapter，内核代码里不允许出现 `if post_type == 1` |
| 与调度模块的钩子引发既有功能回归 | 影响核心业务 | 钩子全部 try/except 且只记日志；接入后跑一遍调度模块的既有测试用例 |
| 视觉语言与现有模块割裂 | 体验不一致 | 大厅虽是浏览型界面，但配色、圆角、间距、字号必须沿用 EleAdminPlus 设计变量，不新造一套 |
| 运营后台审核人力不足 | 审核积压 | 免审白名单 + 批量通过必须在 1.1 就有；上线前和运营确认排班 |
| 二期运单直通时数据模型改不动 | 返工 | `sys_eco_deal` 上预留承接方任务单引用字段与双方租户编码，一期留空 |

## 9. 验收清单

### 9.1 功能验收

- [ ] 配载完成的任务单能一键发布到货源大厅，只需补报价、联系人、展示天数
- [ ] 不满足条件的任务单，发布入口置灰且提示原因清晰
- [ ] 空闲运力能从运力列表一键发布，证照过期的被拦截
- [ ] 手工发布货源/运力可用（不依赖系统单据）
- [ ] 挂牌提交后进入运营审核队列，通过后在大厅可见，驳回后能看到原因并修改重提
- [ ] 免审白名单租户发布后直接上架
- [ ] 大厅筛选（出发地、目的地、时间、台数/位数等）结果正确
- [ ] standard 租户能正常发布挂牌，且被 pro 租户找上门后能完整走完响应→选定→成交→履约→评价
- [ ] standard 租户点击「我要接单」看到的是带真实机会数的升级引导，不是生硬的权限拒绝
- [ ] 挂牌详情向发布方展示需求侧热度（本周被多少家看过、来自哪些地区）
- [ ] 未认证租户不能发布、不能发起意向
- [ ] 发起意向 → 响应 → 双方联系方式解锁 → 选定 → 确认成交，全流程通畅
- [ ] 选定后其余意向自动失效并通知
- [ ] 承接方 24 小时未确认，成交自动作废、挂牌回到展示中
- [ ] 履约节点上报、发布方确认完成、双方互评闭环
- [ ] 完成后能一键把对方加为承运商
- [ ] 任务单被派车/取消后，挂牌自动下架并通知
- [ ] 运力状态变为运输中/解绑后，挂牌自动下架并通知
- [ ] 挂牌到期自动下架
- [ ] 屏蔽名单生效且对被屏蔽方静默
- [ ] 分批承运的台数扣减正确，归零后自动锁定

### 9.2 技术验收

- [ ] 越权用例全部通过（跨租户读写全部被拒）
- [ ] L1 层接口响应体中不含联系方式、企业全称等字段
- [ ] 客户名称、VIN、内部单号、内部成本在平台库中不存在
- [ ] 巡检 Worker 能修复人为制造的不一致
- [ ] 钩子异常不影响派车等既有业务操作
- [ ] `migration.check` 无 drift，snapshot 已同步
- [ ] 运营后台「产品功能清单」全链路体检：无孤儿 feature、无未绑定 feature
- [ ] 后端启动日志无「菜单一致性」告警
- [ ] `seed_client_menus.py` 的前端页面校验无缺失项

### 9.3 体验验收

- [ ] 从任务单到发布成功不超过 3 步
- [ ] 全部文案符合《人性化交互提示语》，无技术黑话
- [ ] 每张卡片都能回答「这家靠不靠谱」
- [ ] 空态有明确的下一步引导，不是干巴巴的「暂无数据」
- [ ] 未读意向在菜单和 Tab 上有角标提示
