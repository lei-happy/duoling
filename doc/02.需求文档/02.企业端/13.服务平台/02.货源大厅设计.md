## 1. 业务场景

### 1.1 谁会发布货源

智途的客户是商品车物流公司。他们的日常是：接到主机厂/经销商的运输计划（运单）→ 配载成任务单（一板轿运车装 6~11 台商品车）→ 派自有车或外协车执行。

发布货源的动机来自配载完成后的一个具体时刻：**任务单已经配好了，但没车拉。**

| 具体情形 | 发布诉求 |
|---------|---------|
| 旺季爆仓，自有车全部在途，新配载的任务单排不上 | 整单外协出去，找同行拉 |
| 这条线路自己没有回程货，跑过去空返不划算 | 外协给在当地有回程的同行 |
| 临时接的一票急单，超出自己运力半径 | 找目的地附近的同行接手 |
| 长期有某条线路的稳定货量，想找固定的外协伙伴 | 发布长期货源，找长期合作 |

> 这四种情形里，前三种的源头都是**已经存在的任务单**，第四种没有具体单据。所以发布来源必须同时支持「从任务单带出」和「手工填写」，只做前者会丢掉最有商业价值的长期合作场景。

### 1.2 谁会来找货

镜像地，来找货的是「车多货少」的租户：淡季车队闲置、某条线路有稳定回程运力、新开线路想找货养车。他们关心的是**线路是否顺路、时间是否对得上、价格是否划算、对方靠不靠谱**。

### 1.3 为什么发布这件事必须零负担

物流公司的调度员一天要处理几十个任务单，如果发布一条货源要重新填 20 个字段，这个功能就不会有人用。**从任务单发布时，用户只需要补充三样东西：对外报价、联系人、有效期。** 其余全部自动带出。这是本模块能不能跑起来的关键，不是可有可无的体验优化。

## 2. 发布来源

| 来源 | `source_type` | 触发入口 | 一期 |
|------|--------------|---------|------|
| **从任务单发布** | 1 | 任务单列表行操作、任务单详情、调度工作台 | ✓ 主路径 |
| **手工发布** | 3 | 货源大厅「发布货源」按钮 | ✓ 冷启动与长期货源必备 |
| 从运输计划发布 | 2 | 计划管理列表 | ✗ 二期 |

### 2.1 从任务单发布的前置校验

任务单必须同时满足以下条件，否则按钮置灰并给出说明：

| 校验项 | 判据 | 不满足时的提示文案 |
|-------|------|------------------|
| 状态合适 | `task.status = 0`（待派车） | 「只有还没派车的任务可以发布到货源大厅」 |
| 未指派运力 | `capacity_id` 与 `carrier_id` 均为空 | 「这单已经安排了承运方，不需要再找车了」 |
| 未被财务锁定 | `is_locked = 0` | 「这单已进入结算流程，不能对外发布」 |
| 未重复发布 | `biz_eco_post_ref` 中该任务单无活跃挂牌 | 「这单已经在货源大厅展示中，去看看有没有人联系」 |
| 有基本线路信息 | `origin` 与 `destination` 均非空 | 「请先补全起点和终点，同行才能找到你」 |
| 装车时间未过期 | `planned_load_time` 晚于当前时间 | 「计划装车时间已过，请先调整时间再发布」 |

> 关于状态限制的取舍：理论上 `status = -1`（待分配）的任务单也可以发布，但那个阶段配载可能还在调整，信息不稳定。限定在「待派车」这一个状态，语义最清晰——货已经配好了、就差车。这与需求描述的「配载完成后」完全对应。

### 2.2 自动带出的字段映射

| 挂牌字段 | 取值来源 |
|---------|---------|
| 起点省市区 / 名称 | `task.origin`、`task.origin_region_id` |
| 终点省市区 / 名称 | `task.destination`、`task.destination_region_id` |
| 分段数 | `task.segment_count` |
| 总台数 | `task.total_quantity` |
| 商品车品牌车系明细 | 经 `biz_task_waybill_item` → `biz_waybill_cargo` 聚合出品牌、车系、台数 |
| 期望装车时间 | `task.planned_load_time` |
| 期望到达时间 | `task.planned_arrive_time` |
| 标题 | 自动生成：`{起点市}→{终点市} {总台数}台 {主要品牌}` |
| 发布企业 | 当前租户 |

**明确不带出的字段**（这些是商业机密，绝不进入平台库）：

- 客户名称与客户 ID（`biz_waybill.customer_id` 关联的客户）
- 内部运费与成本（`carrier_cost_amount`、计费引擎算出的收入）
- 内部单号（`task_no`、`waybill_no`）
- 具体 VIN 码
- 收发货联系人与详细地址（只带到区县级，详细地址在成交后线下沟通）

> VIN 码要特别注意：它是商品车的唯一标识，公开出去等于把主机厂的发运数据暴露给同行，是严重的客户信息泄露。挂牌上只展示「品牌 + 车系 + 台数」。

## 3. 货源挂牌信息模型

> 以下为业务字段分组说明，用于评审信息完整性；类型、长度、索引见第二版数据库设计。

### 3.1 内核通用字段（`sys_eco_post`，两个大厅共用）

| 分组 | 字段 | 说明 |
|------|------|------|
| 身份 | 挂牌编号、挂牌类型（1 货源 / 2 运力）、归属租户、发布人 | 挂牌编号对外展示，便于沟通时互相指认 |
| 展示 | 标题、状态、下架原因、置顶标记 | 标题自动生成，允许用户改写 |
| 来源 | 来源类型、源单 ID、源单快照时间 | 来源类型为手工时源单 ID 为空 |
| 有效期 | 生效时间、失效时间 | 默认 7 天，可选 1/3/7/15/30 天 |
| 联系 | 联系人姓名、联系人手机、备用联系方式 | 默认脱敏，解锁规则见 `04` §3 |
| 可见性 | 可见层级配置、是否公开企业全称、是否应用屏蔽名单 | 见 `04` §3 |
| 统计 | 浏览数、意向数、最后活跃时间 | 冗余字段，用于排序与热度展示 |
| 审核 | 审核状态、审核时间、审核人、驳回原因 | 与 `sys_eco_post_audit` 流水配合 |
| 审计 | 创建人/时间、更新人/时间、软删除标记 | 沿用 `PlatformModelBase` |

### 3.2 货源专有字段（`sys_eco_cargo_post`）

| 分组 | 字段 | 必填 | 说明 |
|------|------|------|------|
| **线路** | 起点省/市/区、起点地名 | ✓ | 精确到区县，不含详细地址 |
| | 终点省/市/区、终点地名 | ✓ | 同上 |
| | 途经点、参考里程 | ✗ | 有多段时展示 |
| **货物** | 货物类别（1 商品车 / 2 普货 / 3 其他） | ✓ | 默认商品车 |
| | 品牌车系明细（品牌、车系、台数，可多行） | ✓ | 商品车类别时必填 |
| | 总台数 | ✓ | 计量单位随货物类别切换：台 / 吨 / 立方 / 件 |
| | 计量单位 | ✓ | 兼容非商品车场景 |
| | 车辆状态（新车 / 二手车 / 试驾车） | ✗ | 影响承运方的装载与保险判断 |
| **承运要求** | 需要车型（轿运车位数区间、平板、封闭厢式） | ✗ | 多选 |
| | 是否接受分批承运 | ✓ | 默认否；接受分批时同一挂牌可成交多方（见 §5.5） |
| | 是否需要承运方投保 | ✗ | |
| | 其他要求 | ✗ | 自由文本，如「需要二层位」「不接受中转」 |
| **时间** | 期望装车时间（起 / 止） | ✓ | 区间而非时点，给承运方留弹性 |
| | 期望到达时间 | ✗ | |
| | 时间是否可协商 | ✓ | 默认可协商 |
| **报价** | 计价方式（1 包车价 / 2 按台价 / 3 面议） | ✓ | |
| | 期望价格、是否含税 | 条件必填 | 计价方式非「面议」时必填 |
| | 结算方式（现结 / 月结 / 预付比例） | ✗ | |
| | 价格是否可议 | ✓ | 默认可议 |
| **合作** | 合作类型（1 单次 / 2 长期线路） | ✓ | 长期线路挂牌的有效期可设更长 |
| | 预计货量频次 | ✗ | 长期合作时填写，如「每周 3~5 车」 |

### 3.3 计量单位的处理

商品车物流按「台」计量，这是本平台的主场景。但为了不把模块限死在单一行业，货物类别切换为「普货」时，计量单位切换为吨/立方/件，品牌车系明细区域隐藏，改为「货物名称 + 重量 + 体积 + 包装方式」。一期先把商品车做扎实，普货字段留出但不做深度优化。

## 4. 大厅浏览与匹配

### 4.1 筛选维度

找货的核心是「顺不顺路、时间对不对得上」，筛选设计围绕这两点：

| 筛选项 | 形式 | 说明 |
|-------|------|------|
| **出发地** | 省 / 市级联，可多选 | 支持「只选省」做模糊匹配 |
| **目的地** | 省 / 市级联，可多选 | |
| **装车时间** | 日期范围快捷项：今天 / 3 天内 / 7 天内 / 自定义 | 默认不限 |
| 台数范围 | 区间输入 | 用于「我的车只能装 8 台」这类过滤 |
| 商品车品牌 | 多选（取自平台品牌库） | |
| 需要车型 | 多选 | |
| 计价方式 | 单选 | 「只看有明确报价的」是高频诉求 |
| 合作类型 | 单选：单次 / 长期 | |
| 发布企业 | 只看已认证 / 只看信誉良好 | 默认勾选「只看已认证」 |
| 关键词 | 文本 | 匹配标题与其他要求 |

### 4.2 排序

| 排序项 | 默认 | 说明 |
|-------|------|------|
| 最新发布 | ✓ | 时效性优先 |
| 装车时间最近 | | 「今天就要装的优先」 |
| 台数从多到少 | | |
| 发布企业信誉 | | 需要信誉数据积累后才有意义，1.3 期开放 |

> 一期**不做**智能排序与推荐。挂牌量少的时候，任何推荐算法的效果都不如「按时间倒序 + 好用的筛选」。等成交数据积累到一定量，二期再基于「历史成交线路相似度」做推荐。

### 4.3 我的常跑线路

企业名片里维护的「主营线路」可以一键作为筛选条件，避免每次进大厅都重新选省市。这是一个成本很低但对留存影响很大的细节：调度员每天来看的其实就是那两三条线。

### 4.4 订阅提醒（1.4 期）

用户可以把当前筛选条件保存为订阅（如「杭州出发 → 川渝方向，8 台以上」），有新挂牌命中时生成工作台待办。这是把「用户来找货」变成「货来找用户」的关键一步，也是提升日活的主要手段。

## 5. 从意向到成交

> 意向单与成交单的通用状态机在 `01` §4.3、§4.4 定义，本节只说货源场景下的具体规则与信息。

### 5.1 发起意向时填什么

找货方点「我想接这单」时，需要提供足以让发布方判断的信息：

| 字段 | 必填 | 说明 |
|------|------|------|
| 报价 | ✓ | 与挂牌计价方式对齐；挂牌为面议时此处必填 |
| 可承接台数 | ✓ | 挂牌接受分批时可小于总台数 |
| 可安排的车型与数量 | ✗ | 如「2 台 8 位板车」 |
| 可装车时间 | ✓ | 用于判断时间是否对得上 |
| 附言 | ✗ | 「这条线我每周都跑，有回程」这类信息往往是成交关键 |
| 关联我的运力挂牌 | ✗ | 如果自己在运力大厅有挂牌，可以一键关联，让对方直接看到车况 |

> 最后一项是两个大厅联动的巧妙之处：找货方把自己的运力挂牌附上，发布方点开就能看到车型、位数、当前所在地和这家企业的信誉，判断效率大幅提升。这是「双边市场共用内核」带来的自然收益。

### 5.2 发布方看到什么

意向列表按「报价 + 可承接台数 + 对方信誉」三列并排展示，支持排序。每条意向可展开看对方的企业名片与关联运力。

发布方的三个动作：**响应**（开始洽谈，互相解锁联系方式）、**婉拒**（需选原因）、**选定**（进入成交）。

婉拒原因选项：价格不合适 / 时间对不上 / 车型不匹配 / 已选择其他合作方 / 其他。这些数据用于二期优化匹配，也让被拒方知道该改什么。

### 5.3 选定与成交确认

发布方选定某个意向后：

1. 该意向状态 → 已选定，生成成交单（状态 0 待确认）
2. 挂牌状态 → 已锁定，从大厅移出
3. 其余意向状态 → 已失效，各自收到通知
4. 承接方收到「被选定」通知（含短信）

承接方需在 **24 小时内确认**，否则成交单自动作废、挂牌回到展示中、其余意向恢复为待响应。这个超时机制防止发布方被单方面吊着。

### 5.4 成交单记录什么

| 分组 | 字段 |
|------|------|
| 双方 | 发布方租户、承接方租户、双方联系人与电话 |
| 标的 | 关联挂牌、关联意向、承接台数、线路、装车时间 |
| 价格 | 成交价、计价方式、是否含税、结算方式 |
| 状态 | 成交状态、确认时间、完成时间、终止原因 |
| 履约 | 承运车牌与司机（承接方在首个节点上报时填写） |
| 衔接 | 是否已建立承运商关系、承接方任务单引用（二期运单直通用） |

### 5.5 分批承运的处理

挂牌勾选「接受分批承运」时，一个挂牌可以对应多个成交单：

- 每次选定一个意向，生成一个成交单，扣减挂牌的「剩余可承接台数」
- 剩余台数 > 0 时，挂牌保持展示中，继续接收意向
- 剩余台数归零时，挂牌转为已锁定/履约中

这是商品车物流的常见场景（一批 30 台车分给 3 家各拉 10 台）。实现上要注意剩余台数的并发扣减，用乐观锁或数据库行锁保证不超卖。

## 6. 履约跟踪与闭环

### 6.1 时间线视图

成交单详情页以时间线（`ele-steps` 或自定义 timeline）展示全流程，每个节点带时间、操作人、备注、附件：

```text
● 发布货源            2026-07-25 09:12   张三（杭州XX物流）
● 平台审核通过        2026-07-25 09:41   平台运营
● 收到合作意向 3 条    2026-07-25 10:05 ~ 14:20
● 已选定合作方        2026-07-25 15:30   张三 → 成都YY运输
● 对方确认成交        2026-07-25 16:02   李四（成都YY运输）
● 已安排车辆          2026-07-26 08:15   川A·12345 王师傅
● 已装车              2026-07-26 10:40   [装车照片 3 张]
● 运输中              2026-07-27 09:00   当前位于西安，预计 28 日到达
● 已送达              2026-07-28 14:22   [回单照片 2 张]
● 确认完成            2026-07-28 16:00   张三
● 双方互评完成        2026-07-29
```

这条时间线就是需求里「全流程管理」的具体交付物——发布方随时能回答「我这单货现在到哪了」，而且每一步都有据可查。

### 6.2 完成与评价

- 「确认完成」必须由**发布方**执行，防止承接方单方面宣布完成
- 承接方上报「已送达」后 7 天，发布方未确认则系统自动完成（避免长期挂起），但不计入发布方的「确认及时率」
- 完成后双方各自评价一次，7 天内未评价视为默认好评
- 评价维度：总体评分（1~5 星）+ 标签（准时 / 车况好 / 沟通顺畅 / 报价实在 / 有回程资源）+ 文字（选填）
- 评价一旦提交不可修改，但被评方可以公开回复一次

### 6.3 一键加为承运商

完成评价后，页面显著位置出现引导：**「合作愉快？把成都YY运输加为常用承运商，下次可以直接派单，不用再发大厅。」**

点击后复用现有能力（`biz_carrier` 建档 + `sys_carrier_link` 账号互通），把这次撮合沉淀为长期合作关系。这是整个模块的价值闭环：**大厅负责认识新伙伴，承运商体系负责把伙伴变成常客。**

从平台视角看，用户「不再需要来大厅」不是流失，而是成功——因为他因此更深地绑定在了智途的合作网络里。

## 7. 与任务单的联动

| 方向 | 时机 | 行为 |
|------|------|------|
| 任务单 → 挂牌 | 任务单被指派运力/承运商、状态推进、取消、删除 | 挂牌自动下架（见 `01` §5.3） |
| 任务单 → 挂牌 | 任务单线路/台数/时间被修改 | 挂牌标记「信息已变更」，48 小时未更新自动下架 |
| 挂牌 → 任务单 | 挂牌发布成功 | 任务单列表与详情显示「货源大厅展示中」角标 |
| 挂牌 → 任务单 | 收到意向 | 角标变为「3 人想合作」，点击跳转 |
| 挂牌 → 任务单 | 成交 | 角标变为「已外协给 XX 公司」，并在任务单详情展示成交信息 |
| 挂牌 → 任务单 | 履约完成 | 引导用户「把这单的承运方登记为 XX 公司」，帮助内部数据完整 |

最后一条值得强调：撮合完成后，用户在自己系统里的任务单还是「待派车」。我们应该引导他把承运方回填进去（选择刚成交的对方为承运商），这样内部的成本、结算、报表才完整。**不引导的话，用户会觉得「大厅和我的系统是两张皮」，这是撮合类功能最常见的失败原因。**

## 8. 规则汇总

| # | 规则 |
|---|------|
| 1 | 一个任务单同时只能有一个活跃挂牌（非终态） |
| 2 | 挂牌默认有效期 7 天，最长 30 天；长期合作类型可设 90 天 |
| 3 | 挂牌编辑后需重新审核；仅修改联系人与报价时走快速复审（见 `04` §2.4） |
| 4 | 同一租户对同一挂牌只能有一个有效意向 |
| 5 | 承接方需在 24 小时内确认成交，超时自动作废 |
| 6 | 发布方在「已锁定」状态可撤销选定，挂牌回到展示中，需说明原因并计入信誉 |
| 7 | 履约中的成交单终止需双方同意或运营介入 |
| 8 | 挂牌详情、联系方式、企业全称的可见性由可见层级统一控制，后端裁剪而非前端隐藏 |
| 9 | 挂牌正文中出现手机号、微信号、QQ 号一律拦截，提示走平台联系（见 `04` §2.3） |
| 10 | 客户名称、内部单号、VIN、内部成本永不进入平台库 |
