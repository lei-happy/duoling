## 1. 业务场景与关键差异

### 1.1 谁会发布运力

| 情形 | 发布诉求 |
|------|---------|
| 淡季车队闲置，车停在场站里 | 找活干，摊薄固定成本 |
| 送完货在外地，需要回程货 | 找返程货，避免空返 |
| 新买了几台车，产能还没消化 | 找长期货源养车 |
| 某条线路常年有富余运力 | 找固定的长期合作方 |

### 1.2 运力挂牌与货源挂牌的三个本质差异

这三点决定了运力大厅不能简单照抄货源大厅的交互：

| 差异 | 货源挂牌 | 运力挂牌 | 设计影响 |
|------|---------|---------|---------|
| **时效性** | 一票货，拉完就没了，天然一次性 | 一台车，这周空、下周可能也空，是**持续可用的资源** | 运力挂牌需要「可用时间窗」而非「单次时间点」，且成交后不一定下架 |
| **稀缺方向** | 货是需求，找车 | 车是供给，找货 | 运力挂牌的核心卖点是「我什么时候、在哪、能去哪」，不是「我有什么车」 |
| **实体粒度** | 一个任务单 = 一条挂牌 | 可能是**一台车**，也可能是**一个车队打包** | 需支持单台与批量两种挂牌粒度 |

其中第一点最容易被忽略：**如果照抄货源的「成交即下架」，一个车队每周都要重新发布一遍，用完就废，体验极差。** 运力挂牌应该像一个长期在线的「名片式广告位」，成交只是消耗它的一段档期。

## 2. 发布来源与粒度

| 来源 | `source_type` | 触发入口 | 一期 |
|------|--------------|---------|------|
| **从运力档案发布** | 1 | 运力列表卡片操作、运力详情 | ✓ 主路径 |
| **手工发布（车队打包）** | 3 | 运力大厅「发布运力」按钮 | ✓ |
| 从运力分组批量发布 | 2 | 运力分组页 | ✗ 二期 |

### 2.1 从运力档案发布的前置校验

现有运力实体 `biz_capacity` 是「司机 + 车辆」的绑定关系，运营状态字段如下：

```44:50:d:\zhitu\backend\app\modules\client\models\capacity\self_capacity\capacity.py
    operation_status: Mapped[int] = mapped_column(
        SmallInteger,
        default=1,
        server_default="1",
        nullable=False,
        comment="运力运营状态 1-可接单 2-运输中 3-休假 4-停运 5-维修保养",
    )
```

校验规则：

| 校验项 | 判据 | 提示文案 |
|-------|------|---------|
| 绑定有效 | `status = 1`（绑定中） | 「这台车还没有绑定司机，请先完成绑定」 |
| 运营状态空闲 | `operation_status = 1`（可接单） | 「这台车正在{运输中/休假/停运/维修保养}，暂时不能对外发布」 |
| 未重复发布 | `biz_eco_post_ref` 中无活跃挂牌 | 「这台车已经在运力大厅展示中」 |
| 证照未过期 | 车辆年检、道路运输证、司机驾驶证、司机从业资格证均在有效期内 | 「{证照名称}已过期，请先更新后再对外发布」 |

> 最后一条是运力大厅特有的、也是必须做的校验。把一台证照过期的车推给同行，一旦路上出事，平台责任说不清。恰好平台已有运力宝的证照监控能力（`fleet_compliance`），此处可直接复用其到期判断逻辑；未开通运力宝的租户则用车辆扩展表 `biz_vehicle_ext` 上的到期日期字段做基础校验。

**车辆保险到期不硬拦，改为标红送审**（`SuspiciousFlag.INSURANCE_EXPIRED`）。保险影响的是出事后的理赔与追偿，不是上路合法性，且各家投保节奏差异大（脱保几天再续的情况很常见），硬拦会误伤大量正常运力。但它恰恰是出事时最影响追偿的一项，所以不能当作不存在——命中后写入 `precheck_flags` 让审核员逐条确认，同时**收回免审直通资格**，否则白名单租户的这条提示根本没人看得到。

> 另：**效期字段为空不视为过期**。存量车辆档案普遍没录全效期，把「没填」等同于「过期」会在功能上线第一天就劝退大部分用户。缺失的效期由运力宝的证照补录引导去解决，不在发布环节堵。

### 2.2 自动带出的字段映射

| 挂牌字段 | 取值来源 |
|---------|---------|
| 车牌号 | `biz_capacity.plate_number`（默认打码展示，见 §4.2） |
| 挂车车牌 | `biz_vehicle.trailer_id` → 挂车档案 |
| 车型 / 车长 / 载重 | `biz_vehicle_ext` |
| 轿运车位数 | `biz_vehicle_ext`（若无该字段则本期新增到扩展表，或发布时手填） |
| 司机姓名 | `biz_capacity.driver_name`（**默认只展示姓氏 + 师傅**） |
| 司机手机 | `biz_capacity.driver_phone`（**默认完全隐藏**，见 §4.2） |
| 承运经验 | 由该运力的历史任务单统计（跑过多少单、主要线路） |
| 发布企业 | 当前租户 |

### 2.3 批量与打包挂牌

手工发布支持「一次挂多台」：填写车队规模（如「8 位轿运车 5 台」）而不指定具体车辆。适用场景是车队长想整体推广运力，不想一台台发。

批量挂牌的特点：

- 不关联具体 `biz_capacity`，因此不受单台运力状态联动的影响
- 成交时按「本次承接台数」扣减可用台数
- 由发布方自行维护可用数量，系统在每次成交后提醒「当前还剩 X 台可用，是否需要调整？」

### 3.1 为什么「当前所在地 + 期望流向」是核心

传统运力信息只写「我有 5 台 8 位板车」，这种信息对找车方几乎无用——他关心的是「你的车现在在哪、什么时候能到我这儿装货、装完能不能顺路送到我要的地方」。

**运力大厅的列表卡片主视觉应该是一条线路箭头：`成都（现在空）→ 期望往华东`，而不是车辆参数表。** 参数是次要的过滤条件，位置与流向才是撮合的第一决策依据。这一点在前端设计中要严格贯彻（见 `05` §3.2）。

## 4. 大厅浏览与隐私处理

### 4.1 筛选维度

| 筛选项 | 形式 | 说明 |
|-------|------|------|
| **当前所在地** | 省 / 市级联，可多选 | 最高频，置于第一位 |
| **期望流向** | 省 / 市级联，可多选 | 与所在地组合成「从哪到哪」 |
| **可用时间** | 日期范围快捷项：今天 / 3 天内 / 7 天内 | |
| 车辆类型 | 多选 | |
| 轿运车位数 | 区间 | 商品车物流的关键匹配项 |
| 可载台数 | 区间 | |
| 车辆数量 | 区间 | 「我要一次找 5 台车」 |
| 是否可开票 | 单选 | |
| 合作类型 | 单选 | |
| 发布企业 | 只看已认证 / 只看信誉良好 | 默认勾选「只看已认证」 |

### 4.2 车牌与司机信息的隐私处理

运力挂牌涉及**个人信息**（司机姓名、手机号、身份证），处理规格必须高于货源挂牌：

| 信息 | 匿名层（大厅列表/详情） | 洽谈层（意向被响应后） | 成交后 |
|------|----------------------|---------------------|--------|
| 车牌号 | 打码：`川A·1***5`；发布方可选择完全公开 | 完整 | 完整 |
| 挂车车牌 | 打码 | 完整 | 完整 |
| 司机姓名 | 「王师傅」 | 完整姓名 | 完整姓名 |
| 司机手机 | **完全不返回** | **完全不返回** | 由发布方在履约节点主动提供 |
| 司机身份证 / 驾驶证 | **永不返回** | **永不返回** | 双方线下核验 |
| 企业联系人与电话 | 隐藏 | 完整 | 完整 |

**核心原则：跨租户交易的对接人是企业联系人，不是司机。** 司机的联系方式只在成交并安排车辆后，由发布方在履约上报环节主动填写给对方，而不是作为挂牌的公开信息。这既是个人信息合规的要求（司机没有同意把自己的号码公示给全平台），也避免了「同行直接撬司机」的行业乱象。

> 这条规则要在产品上说清楚，否则用户会问「为什么不能看司机电话」。界面提示：「为保护司机个人信息，联系司机请通过企业联系人安排。」

## 5. 撮合流程的差异点

大部分流程与货源大厅对称，以下三点不同：

### 5.1 发起意向的内容不同

找车方发起意向时填写的是**货的信息**：

| 字段 | 必填 | 说明 |
|------|------|------|
| 货物线路（起点 → 终点） | ✓ | |
| 台数 / 数量与单位 | ✓ | |
| 期望装车时间 | ✓ | |
| 报价 | ✓ | |
| 关联我的货源挂牌 | ✗ | 如果这票货已经在货源大厅挂着，一键关联，对方可直接查看完整信息 |
| 附言 | ✗ | |

> 与货源大厅的「关联运力挂牌」互为镜像，两个大厅通过意向单互相引用，形成完整的双边市场闭环。

### 5.2 成交后挂牌不一定下架

| 情形 | 挂牌处理 |
|------|---------|
| 指定车辆挂牌 + 单次合作 | 转为「履约中」，从大厅移出；履约完成后询问用户「这台车又空了，要不要重新展示？」一键重新上架（需重审，走快速复审） |
| 车队打包挂牌 | 扣减可用台数，**保持展示中**；台数归零时自动转为已锁定 |
| 长期合作类型 | 成交后保持展示中，同时在卡片上展示「已有 N 家在合作」，这本身就是信誉背书 |

这是运力挂牌与货源挂牌最重要的机制差异，`sys_eco_post` 上需要一个 `keep_listed_after_deal` 标记来表达。

### 5.3 履约节点由发布方（车方）上报

货源大厅是承接方上报、发布方确认；运力大厅角色对调：**运力发布方就是承运方**，由它上报节点，找车方确认完成。内核实现上统一为「承运角色上报、货主角色确认」，由成交单上的 `carrier_side` 字段标明哪一方是承运方，避免写两套逻辑。

## 6. 与运力档案的联动

| 源单变化 | 挂牌处理 | 通知 |
|---------|---------|------|
| `operation_status` 变为 2 运输中 | 自动下架（原因 4） | 「{车牌}已开始运输，运力信息已自动停止展示」 |
| `operation_status` 变为 3/4/5（休假/停运/维修） | 自动下架（原因 4） | 同上，文案替换 |
| `operation_status` 变回 1 可接单 | **不自动上架**，生成待办提醒「{车牌}又空了，要不要重新发布到运力大厅？」 | 待办 |
| 运力解绑（`status=0`） | 自动下架（原因 4） | 「{司机}已从{车牌}下车，运力信息已自动停止展示」 |
| 车辆或司机档案被删除 | 自动下架（原因 4） | 通知 |
| 证照到期 | 自动下架（原因 4） | 「{证照}已到期，为避免合作风险，运力信息已自动停止展示。更新后可重新发布」 |

> 「不自动上架」是刻意的设计。自动上架会让用户失去对「我的车什么时候在对外展示」的掌控感，一旦某次不想对外接单却被自动挂出去，用户对整个功能的信任就没了。**自动下架是保护，自动上架是冒犯。**

### 6.1 运力列表的展示增强

运力列表（`/capacity/self-capacity/list`）的卡片上增加大厅状态角标：

| 挂牌状态 | 角标 | 点击行为 |
|---------|------|---------|
| 展示中 | 「运力大厅展示中」 | 跳转挂牌详情 |
| 有意向 | 「3 家想合作」（强调色） | 跳转意向列表 |
| 已成交 | 「已接单：XX 物流」 | 跳转成交详情 |
| 未发布 + 可接单 + 空闲超 3 天 | 「空闲 5 天，去大厅找货？」（弱提示） | 打开发布弹层 |

最后一条是主动的价值触达：系统知道哪些车闲着，主动提醒比等用户想起来有效得多。但要控制频率，同一台车 7 天内只提示一次，避免打扰。

## 7. 规则汇总

| # | 规则 |
|---|------|
| 1 | 一个 `biz_capacity` 同时只能有一个活跃挂牌 |
| 2 | 证照过期的运力不允许发布，已发布的自动下架 |
| 3 | 司机手机号、身份证、驾驶证在任何可见层级下都不返回给其他租户 |
| 4 | 车牌默认打码，发布方可选择完全公开 |
| 5 | 运力挂牌默认有效期 15 天（长于货源，因为运力信息时效性相对弱），长期类型可设 90 天 |
| 6 | 车队打包挂牌的可用台数由发布方维护，每次成交后提醒核对 |
| 7 | 运力状态恢复空闲时不自动上架，仅提醒 |
| 8 | 履约节点由承运方（运力发布方）上报，货主方确认完成 |
| 9 | 运力大厅与货源大厅的意向可互相关联引用 |
