## 二、开发阶段规划

### 阶段一：基础设施完善（预计 1~2 周）

#### 1.1 数据库迁移体系

**目标**：引入 Alembic 迁移管理，告别 ORM 直接建表方式。

- 初始化 Alembic 配置目录（`backend/alembic/`）
- 基于现有 ORM 模型生成基线迁移脚本
- 补充缺失的 ORM 模型（`biz_role_menu`、`biz_user_role`、`biz_department`）
- 后续所有表结构变更通过迁移脚本管理

#### 1.2 创建自有验证企业

**目标**：建立一个"智途科技"测试企业，作为企业端功能的验证环境。

- 通过 Console 或初始化脚本创建企业
- 初始化完整测试数据：组织架构（总公司-部门）、员工账号、角色分配
- 预置示例业务数据（车辆、驾驶员、客户、路线）
- 此企业在后续每个企业端模块开发时用于验证

#### 1.3 文件存储服务

**目标**：搭建通用文件上传/下载模块，为后续所有涉及附件的功能提供基础支撑。

- 后端新增通用文件服务（`backend/app/common/storage.py`）
- 支持本地文件存储，预留 OSS（阿里云/腾讯云）接口
- 文件元信息表（`sys_file`）：原始文件名、存储路径、文件大小、MIME 类型、关联业务
- 前端已有 FileUpload/ImageUpload 共享组件，对接后端上传 API
- 使用场景：车辆证件照片、回单图片、合同附件、企业 Logo 等

### 阶段二：运营后台完善（预计 2~3 周）

#### 2.1 产品版本功能清单管理（核心）

**目标**：实现"不同产品版本控制不同功能菜单"的核心 SaaS 能力。

**数据库设计**：

| 新增表 | 说明 |
|--------|------|
| `sys_product_feature` | 功能清单定义（feature_code, feature_name, description, module） |
| `sys_version_feature` | 版本与功能关联（version_id, feature_id, status） |

**实现要点**：
- Console 端：产品版本详情页新增"功能配置"Tab，可勾选/取消功能项
- 功能清单与菜单关联：每个菜单项可配置 `feature_code`，登录时根据企业所购版本过滤
- Client 端登录时：查询企业授权版本 → 获取功能清单 → 过滤可用菜单
- 需求文档：`doc/需求文档/运营后台/产品版本功能管理.md`

#### 2.2 平台基础资源管理

**目标**：维护平台级公共资源数据，新企业注册时自动同步。

| 资源模块 | 数据库表 | 说明 |
|----------|----------|------|
| 地区库 | `sys_region` | 省/市/区三级联动，来源国家标准行政区划数据 |
| 商品车资源库 | `sys_vehicle_brand` / `sys_vehicle_model` | 品牌/车系/车型层级数据 |
| 经销商资源库 | `sys_dealer` | 经销商基础信息，含地区关联 |

**实现要点**：
- Console 端：各资源的 CRUD 管理页面
- 提供公共查询 API（可供 Client 端和 Open 接口调用）
- 新企业注册时同步逻辑：在 `TenantService.create_tenant` 流程中，将平台资源数据复制到租户库对应表
- 需求文档：`doc/需求文档/运营后台/平台基础资源管理.md`

#### 2.3 系统日志完善

**目标**：完善操作审计和登录记录功能。

**操作日志**：
- 基于装饰器实现自动记录（`@operation_log(module="用户管理", action="创建")`）
- 后端模型 `OperationLog` 已存在，需实现记录逻辑和查询 API
- 前端操作记录页面已就绪，对接即可

**登录日志**：
- 新增 `sys_login_log` 表（用户、时间、IP、设备信息、登录结果）
- 在认证 Service 的登录方法中记录
- 前端登录记录页面已就绪，对接即可

- 需求文档：`doc/需求文档/运营后台/系统日志.md`

#### 2.4 运营数据看板

**目标**：Console Dashboard 对接真实数据。

- 租户统计：总数、本月新增、各生命周期阶段分布
- 活跃度：最近 7 天/30 天登录企业数
- 产品分布：各版本授权数量占比
- 收入概览（预留，待结算模块完成后对接）

### 阶段五：企业端业务模块（预计 4~6 周）-- 核心

> 需求文档：`doc/需求文档/企业端/业务模块-运单管理.md`

#### 5.1 运单管理（核心业务流）

**运单全生命周期**：

```
创建 → 调度（派车/派人） → 装车发车 → 在途 → 到达 → 签收 → 回单 → 结算 → 完成
                                        ↓
                                    异常处理（延迟/货损/事故）
```

- 已有 ORM 模型 `Order`，字段较完整
- 运单创建：关联客户、路线、货物信息、运费
- 运单状态流转：每步操作记录操作人和时间
- 批量操作：批量创建、批量调度、批量签收
- 运单查询：多维度筛选（状态、时间、客户、车辆、驾驶员）
- 运单详情：完整信息展示 + 操作时间线
- 数据导入导出：Excel 批量导入运单、导出运单报表

#### 5.2 调度管理

- 调度看板：当前车辆状态分布、驾驶员状态分布
- 派车操作：选择车辆 + 驾驶员，关联运单
- 换车/换人：运单调度变更
- 调度记录：所有调度操作历史

#### 5.3 在途追踪

- 运单在途状态实时更新
- 异常事件记录（延迟、事故、货损、其他）
- 在途运单地图展示（预留 GPS 集成接口）

#### 5.4 回单管理

- 电子回单上传（拍照/扫描，关联文件存储）
- 回单审核流程（提交 → 审核 → 通过/驳回）
- 回单与运单关联查看

#### 5.5 消息通知

- 站内消息模块（系统通知、业务提醒）
- 消息分类：运单状态变更、审批通知、证件到期提醒、系统公告
- 消息已读/未读管理
- 前端已有 Notice Store，需设计后端消息表和推送逻辑

## 三、技术架构补充规划

### 3.1 数据库迁移（Alembic）

- 阶段一引入，贯穿所有后续开发
- 每个模块的表结构变更都通过迁移脚本管理
- 迁移脚本需支持平台库和租户库双库场景

### 3.2 数据导入导出

- 阶段四/五引入，基于 openpyxl 或 pandas 实现
- 通用导入框架：模板下载 → 填写 → 上传 → 校验 → 入库
- 通用导出框架：查询条件 → 后端生成 → 前端下载

### 3.3 消息通知体系

- 阶段五引入
- 站内消息：WebSocket 实时推送（或轮询）
- 外部通知：短信/邮件（预留接口，按需集成）
- 微信推送：模板消息（移动端阶段对接）

### 3.4 定时任务

- 基于 APScheduler 或 Celery Beat
- 产品授权过期检查（每日 02:00）
- 证件到期提醒（每日 08:00 检查 7 天内到期的车辆/驾驶员证件）
- 数据统计汇总（每日凌晨预计算 BI 报表数据）
